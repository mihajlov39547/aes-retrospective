\section{Discussion}
\subsection{What the results establish}
The strongest result is \emph{implementation-path sensitivity under documented timing boundaries}. On Oracle Arm64, default EVP is much faster than the inspected alternative paths for AES-128-CTR at 32 MiB. On Windows, using an inner EVP timer makes OpenSSL appear considerably faster than PyCryptodome; expanding the observation to a broader software operation substantially narrows that advantage. Thus a claim such as ``CPU AES achieves 5.5 GB/s'' is incomplete without declaring whether the caller is reusing contexts and buffers.

A second observation concerns protected workloads rather than just AES round computations. At 1 KiB, authenticated GCM decryption plus verification can be much slower than at larger sizes when expressed as bytes per second. The AES key length also affects CBC and GCM performance. These data should not be collapsed into one architecture score; they address different cipher modes, key schedules and functional requirements.

\subsection{Potential applications and transferability}
The most direct engineering application is benchmark and service design for CPU-based encryption components. A storage system, secure message processor or key-management service that repeatedly invokes a cryptographic API should benchmark the actual operation envelope, not only the cipher core. Systems handling large sequential buffers might benefit from native EVP processing and buffer reuse; systems dominated by small authenticated messages may see relatively greater importance of setup and tag verification. This is a plausible design implication, not a measured speedup of a particular storage product or network protocol.

The generalizable element is the methodology, not the numerical ordering of processors. A useful performance report should identify the cipher and mode; key size and nonce/AAD policy; library version and capability dispatch; input residency and buffer policy; transform versus operation timing; and the distribution of session-level observations. The observations from an Arm64 virtual machine and a Windows laptop motivate such reporting across architectures, but do not themselves constitute a matched hardware shootout.

The presence of an additional historical Windows workstation does not remove this limitation. Since that machine lacks a directly comparable archived new EVP campaign, adding its CPU/GPU values to the present paper would manufacture comparability and overlap with a different submitted study. Likewise, comparing the Oracle CPU directly with a separately timed GPU would be misleading.

\subsection{Threats to validity and future research}
This retrospective study is constrained by nonidentical APIs, differences in library versions, unpinned operating-system scheduling, DVFS and cloud virtualization. Default OpenSSL capability inspection is not a trace of executed instructions. The Arm capability mask disables multiple instruction classes at once, so a causal claim about any one extension is not warranted. The 32 MiB measurements reuse prepared data, and their cache and memory-allocation behavior may differ from a streaming application. The five seeds produce useful repetition within a platform, not a representative sample of processors. The AES-GCM and CBC campaigns use different timing conventions from the newer CTR experiments.

There are several clearly bounded follow-up studies: (i) use identical native entry points and output-buffer reuse on both architectures; (ii) trace hardware instructions and isolate AES, vector and polynomial-multiply dispatch controls independently; (iii) measure GCM on Arm64 with matched nonce, associated-data and tag-validation policies; (iv) compare single-thread latency and two-worker aggregate throughput under a common process-orchestration protocol; and (v) validate encryption in a real application with request formation, input/output copying and persistent storage or network I/O. Those are future experiments, not results claimed here.

The retained reduced-keyspace and avalanche demonstrations from the larger retrospective have been intentionally excluded. Their principal questions concern educational cryptanalysis and diffusion, rather than CPU encryption costs; including them would weaken the coherence of this implementation-boundary study.
