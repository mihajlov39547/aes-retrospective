\section{Conclusion}
\label{sec:conclusion}
The experiments identify a specific opportunity rather than a blanket GPU
advantage: with 32 independent 1~MiB pages, Tesla T4 AES-128-CTR resident
execution is approximately $2.251\times$ faster than native OpenSSL EVP
transformation at the measured compute boundaries. Once the prepared GPU path
includes synchronous host--device transfers and synchronization, that ratio
falls to $0.913\times$ and the CPU wins in all five sessions. A page-aware
kernel with independent counter domains has approximately the same GPU
pipeline throughput as a continuous stream of equal size, but this does not
establish an acceleration benefit over separate per-page launches.

A second key finding is baseline sensitivity: the new T4 study reports a
$5.586\times$ prepared-pipeline ratio relative to PyCryptodome but
$0.942\times$ relative to native OpenSSL. Consequently, library choice and
measurement boundaries are essential to any defensible GPU acceleration
claim. Earlier three-platform measurements remain historical evidence tied to
their original host implementation, not proof of an optimized-CPU advantage.

The practical candidate is an application that already keeps its input and
subsequent ciphertext consumer on the GPU; in such a pipeline encryption can
potentially exploit device-resident computation without paying a full payload
round trip. This is an engineering hypothesis supported by the isolated
resident result, not an established application speedup. Future work should
measure a complete GPU-native producer--encrypt--consumer pipeline against an
equivalent CPU workload and separately test one-page-per-launch overhead,
Parquet-compliant authenticated storage processing, and overlapping data
movement. The principal finding is therefore a reproducible boundary between
GPU computational gain and transfer-limited execution, together with a
validated independent-page workload for investigating that boundary.
