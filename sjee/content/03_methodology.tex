The CPU path uses PyCryptodome with AES-NI explicitly enabled~\cite{pycryptodome}. Native backend
initialization is checked separately for ECB and CTR; this supports the intended dispatch but
is not an instruction trace. The CUDA path is the validated implementation archived as
\texttt{cuda\_baseline}, invoked through CuPy~\cite{cupyRawKernel}. It assigns one AES block to
each thread, with 128 threads per CUDA block. This implementation is a reproducible comparator,
not a claim of maximum GPU AES performance.

The article selects this CUDA path and AES-NI from a broader archived campaign. Other CPU and
CUDA paths were interleaved in the original execution schedule but are excluded from the
reported comparisons. No measurements were rerun or altered for this selection. It retains
9,000 observations from the original 18,000, while preserving all fifteen sessions and every
size/mode combination for the selected paths.

\subsection{Validation and Paired Workloads}
\label{subsec:experimental_design}

Cryptographic checks precede accepted performance measurements. Known-answer tests and
cross-backend comparisons use the AES and mode specifications~\cite{nist2023aes,dworkin2001modes}.
The archived validation records document successful CUDA execution and agreement with CPU
references. Correctness is necessary but does not establish timing reliability; completeness,
configuration consistency and artifact integrity are checked separately.

The workload is AES-128 encryption in ECB and CTR at 1~KiB, 16~KiB, 1~MiB, 16~MiB and 32~MiB.
ECB is a performance probe, not a recommendation for securing structured application data.
Inputs and cryptographic parameters are generated deterministically and shared by the paired
CPU and GPU jobs. Each system contributes five sessions, with seeds 2003--2007, five warmups
and twenty measured repetitions per group. Warmups are excluded from the exports and are
supported by configuration and source provenance. The retained subset has thirty groups and
600 observations per session.

Sizes execute in fixed ascending order; mode and backend/scope jobs are shuffled using the
session seed. Experiments run sequentially, without concurrent benchmark jobs. The original
ordering is retained in the evidence, including jobs excluded from this article. Sessions are
repeated executions on the same host, not independently sampled machines.

\subsection{Measurement Boundaries}
\label{subsec:measurement_boundaries}

Host wall timing uses \texttt{time.perf\_counter\_ns()}. The three intervals are distinct:
\begin{itemize}
  \item \textbf{CPU transform:} the encryption call, including output allocation but excluding
    cipher construction and key setup.
  \item \textbf{GPU resident:} a single kernel launch timed with CUDA events; transfers occur
    outside the interval. The resident-iteration count is one.
  \item \textbf{GPU pipeline:} host wall time for the synchronous H2D--kernel--D2H sequence,
    including launch and required synchronization, using prepared pinned host buffers and
    preallocated device buffers.
\end{itemize}

GPU compilation, allocation, pinning, initial staging, key preparation and application I/O are
outside these intervals. The pipeline is consequently not full application encryption.
Resident event timing and pipeline wall timing are not interchangeable observations of one
interval~\cite{cupyPerformance}. Recorded copy intervals include synchronization; subtracting
resident time from pipeline time cannot identify pure PCIe transfer latency.

\subsection{Statistics and Reproducibility}
\label{subsec:statistical_analysis}

For payload size $N$ bytes and elapsed time $T_{s,r}$ in session $s$, repetition $r$, throughput
is $R_{s,r}=N/(10^6 T_{s,r})$ in decimal MB/s. Input labels use binary KiB and MiB. We first
compute the median of each session's twenty latency and throughput observations, then aggregate
across sessions:
\begin{equation}
  \widetilde{T}=\operatorname{median}_{s}\bigl(\operatorname{median}_{r}T_{s,r}\bigr),
  \qquad
  \widetilde{R}=\operatorname{median}_{s}\bigl(\operatorname{median}_{r}R_{s,r}\bigr).
  \label{eq:study_estimates}
\end{equation}

Throughput is summarized independently rather than obtained by inverting the aggregate latency.
For each size, mode and GPU scope, paired speedup is
\begin{equation}
  S_s=\frac{\widetilde{T}_{\mathrm{AES\mbox{-}NI},s}}
              {\widetilde{T}_{\mathrm{GPU},s}},
  \qquad \widetilde{S}=\operatorname{median}_{s=1,\ldots,5}S_s.
  \label{eq:study_speedup}
\end{equation}

Values above one favor the GPU. We report session ranges, interquartile ranges and sample
coefficients of variation (CV = sample standard deviation/mean), together with directional
counts. A $5/5$ gain is observed consistency, not a significance test. Repetitions are not pooled
as independent sessions, no outliers are removed, and systems retain their own CPU references.

Configurations, raw observations, validation records, source snapshots and SHA-256 hashes are
archived under one selected run per system. The retained estimators were independently
reconstructed from native raw CSVs, including the authoritative T4 archive, and agreed with
saved aggregates within relative tolerance $10^{-10}$ and absolute tolerance $10^{-15}$.
Active benchmark source snapshots match across systems; software environments and compiled
binaries need not. The accompanying evidence mapping records run IDs, seeds, raw-file hashes
and the selection, while the manuscript's offline figure script reproduces the retained tables
and plot without executing benchmarks.
