
\section{Methodology}
\label{sec:methodology}

This study adopts a validation-first experimental methodology for
evaluating AES implementations across heterogeneous CPU and GPU
execution environments. The objective is to distinguish
cryptographic correctness from performance, explicitly define
the operations included in each timed interval, and preserve
sufficient experimental evidence for independent verification.

Rather than treating encryption throughput as an intrinsic
property of AES, the methodology evaluates specific execution
paths under documented hardware and software conditions.
The experimental design combines deterministic workload
generation, paired CPU--GPU comparisons, repeated study
sessions, hierarchical statistical aggregation, and
machine-readable provenance.

The principal heterogeneous study evaluates three computing
configurations: two Windows laptop systems equipped with
4~GB NVIDIA GPUs and a Linux-based Google Colab environment
equipped with an NVIDIA Tesla T4.

The methodology is intended to support reproducible comparisons
of measured implementation paths, not to establish universal
performance rankings or demonstrate a new cryptographic
algorithm.

\subsection{Experimental Platforms}
\label{subsec:experimental_platform}

The experiments were conducted on three distinct hardware
and software configurations.

The first platform consisted of an Intel Core i5-10300H
processor with 16~GB of system memory and an NVIDIA
GeForce GTX~1650~Ti GPU equipped with 4~GB of device
memory. The system operated under Microsoft Windows~10
and represented a consumer laptop GPU environment.

The second platform consisted of an Intel Core i7-11850H
processor and an NVIDIA T600 Laptop GPU with 4~GB of
device memory. The system operated under Windows~11
and represented an entry-level professional mobile
GPU configuration.

The third platform was a Google Colab Linux environment
equipped with an NVIDIA Tesla T4 datacenter GPU.
The GPU provided approximately 15~GiB of accessible
device memory. The host environment exposed an Intel
Xeon CPU identified as operating at 2.00~GHz, with
two logical processors available to the benchmark.
The precise host processor SKU was not established
by the collected environment metadata.

CPU cryptographic operations and reference calculations
were implemented using PyCryptodome~\cite{pycryptodome}.
The reported CPU performance therefore characterizes
specific library execution paths rather than the maximum
attainable throughput of AES on the underlying processor.

The GPU implementations were executed using CUDA kernels
integrated through CuPy. The CUDA programming environment
provides kernel invocation, device-memory management,
host--device transfers, and synchronization mechanisms
\cite{nvidiaProgrammingGuide,cupyRawKernel}.

The Windows configurations operate within the Windows
GPU driver environment. Command scheduling, preemption,
and synchronization may contribute to execution variability
\cite{microsoftGpuPreemption,microsoftTdr}.
The Linux/Colab configuration employs a different driver
and runtime environment.

These differences are documented as potential confounding
factors. The study does not isolate the causal effects
of the operating system, GPU product category, CPU
architecture, or software-library version.

Accordingly, each platform is treated as a complete
hardware--software configuration. GPU throughput is
compared using matched workloads, while CPU--GPU
speedups are computed relative to the CPU belonging
to the same platform.


\subsection{Validation-First Experimental Protocol}
\label{subsec:validation_protocol}

Functional correctness is a prerequisite for accepting
performance measurements.

Before the corresponding benchmark results are admitted
to the principal analysis, cryptographic implementations
must pass the required correctness checks.

The validation procedures include known-answer test
vectors, comparisons with reference CPU implementations,
and consistency checks between supported execution
backends.

Expected AES behavior is defined using the applicable
cryptographic standards and mode specifications
\cite{nist2023aes,dworkin2001modes,dworkin2007gcm}.

PyCryptodome provides reference cryptographic operations
used for selected CPU--GPU validation procedures
\cite{pycryptodome}.

The validation process is designed to prevent
incorrect or incomplete encryption operations from
being reported as successful high-throughput
implementations.

The benchmarking workflow distinguishes three
execution profiles:

\begin{enumerate}

\item \textbf{Smoke profile.}
A lightweight functional check used to verify
cryptographic correctness, execution arguments,
software dependencies, and artifact generation.

\item \textbf{Pilot profile.}
A preliminary measurement procedure used to
inspect execution behavior and verify that the
selected experimental parameters are operationally
suitable.

\item \textbf{Study profile.}
The controlled experimental configuration used
to generate the observations included in the
principal performance analysis.

\end{enumerate}

Only the selected complete study-profile runs
contribute to the principal three-platform
comparison. Developmental, smoke, pilot, and
historical runs are not pooled with these results.

The protocol preserves random seeds, workload
definitions, execution arguments, validation
outcomes, software and hardware metadata, and
source-code snapshots.

Cryptographic correctness and methodological
integrity are treated as distinct requirements.

Passing a known-answer test establishes agreement
with the expected cryptographic transformation
under the tested conditions. It does not prove
that an execution timer is unbiased or that
system-level interference is absent.

The methodology therefore complements functional
validation with checks of dataset completeness,
input pairing, implementation identity, timing
definitions, and reproducibility of the statistical
calculations.


\subsection{Workload Definition and Paired Experimental Design}
\label{subsec:experimental_design}

The primary heterogeneous comparison evaluates
AES-128 encryption in Electronic Codebook (ECB)
and Counter (CTR) modes.

Both modes permit independent block-level
processing, making them suitable for controlled
comparisons of CPU and CUDA implementations
\cite{dworkin2001modes}.

ECB is used as an implementation-performance
probe rather than as a recommended mode for
securing general application data.

CTR results characterize the tested encryption
operation and do not include authentication
or complete application-level nonce-management
procedures.

Five workload sizes were selected:

\begin{equation}
N \in
\left\{
2^{10},
2^{14},
2^{20},
2^{24},
2^{25}
\right\}
\text{ bytes}.
\label{eq:workload_sizes}
\end{equation}

These correspond to 1~KiB, 16~KiB, 1~MiB,
16~MiB, and 32~MiB.

The selected range includes small workloads,
where fixed execution overhead can dominate,
and larger buffers, where computational throughput
and data-transfer costs become increasingly relevant.

The CPU comparisons include two reference paths:
a selected software AES implementation and a
hardware-accelerated AES-NI implementation.

The GPU comparisons include two timed CUDA
implementations: a baseline kernel and an
optimized-v1 candidate.

The optimized-v1 implementation is evaluated
as a separate implementation candidate, without
assuming that it provides a performance advantage
for every workload.

For each configuration, the CPU and GPU paths
use matching cryptographic input data and
parameters, including plaintext, AES keys,
and mode-dependent values.

The deterministic session seeds were:

\begin{equation}
s \in \{2003,2004,2005,2006,2007\}.
\label{eq:study_seeds}
\end{equation}

Each platform contributed five study sessions.

Within each session, every measured configuration
used five warm-up executions followed by
twenty recorded timing repetitions.

The warm-up observations were excluded from
the reported performance statistics.

The principal benchmark contains 60 measured
configuration groups per session, yielding
1,200 raw timing observations for each session.

Across the three configurations, the complete
heterogeneous study therefore contains

\begin{equation}
3 \times 5 \times 1200 = 18\,000
\label{eq:raw_observation_count}
\end{equation}

recorded timing observations.

These 18,000 observations are nested within
15 study sessions and are not treated as
18,000 independent experimental replications.

Fixed seeds improve the traceability of workload
identity but do not eliminate variability caused
by hardware clocks, operating-system scheduling,
memory behavior, or runtime execution.

Furthermore, workload sizes were executed in a
fixed order rather than a randomized sequence.
Possible ordering effects are therefore
acknowledged as a limitation of the study.

The paired design improves comparability of
CPU--GPU measurements, but the corresponding
execution paths do not necessarily include
identical host-side operations.

Their timing boundaries are consequently defined
and interpreted separately.


\subsection{Measurement Boundaries}
\label{subsec:measurement_boundaries}

The explicit definition of measurement boundaries
is a central component of the experimental
methodology.

Four principal execution paths are distinguished.

\begin{enumerate}

\item \textbf{CPU software path.}
Measures the selected software AES encryption
operation executed on the host processor.

\item \textbf{CPU AES-NI path.}
Measures the corresponding encryption operation
using the selected hardware-accelerated CPU
library backend.

\item \textbf{GPU resident path.}
Measures CUDA kernel execution with input data
already present in device memory, excluding
host-to-device and device-to-host transfers.

\item \textbf{Prepared-buffer GPU pipeline path.}
Measures the defined synchronous processing
sequence comprising host-to-device transfer,
CUDA kernel execution, device-to-host transfer,
and the synchronization required to complete
the sequence.

\end{enumerate}

CPU measurements describe the selected
cryptographic transformation call.

The measured CPU boundary includes output
allocation performed by the cryptographic
library call but excludes cipher construction
and application initialization.

The GPU resident measurement characterizes
kernel execution independently of the transfers
required to move data between host and device.

GPU buffers and input preparation occur
outside the resident timing interval.

The GPU pipeline uses preallocated device
memory and prepared pinned host buffers.

Pinned memory can support efficient data
transfers, although its use does not
automatically imply overlapping transfer
and computation
\cite{nvidiaProgrammingGuide,nvidiaBestPractices}.

The measured pipeline follows a synchronous
sequence and does not implement a separately
evaluated multi-stream asynchronous
transfer/compute configuration.

The pipeline boundary includes the selected
H2D copy, kernel invocation and completion,
D2H copy, and required synchronization.

However, several operations are performed
outside this boundary.

These include host-buffer allocation and
pinning, initial staging into the prepared
buffers, device allocation, CUDA compilation,
cipher initialization, and cryptographic
key preparation.

The boundary also excludes external file
operations, networking, application-level
authentication, and service orchestration.

Consequently, the term \emph{prepared-buffer
pipeline} is used to identify this broader
GPU timing scope.

Where the expression \emph{end-to-end} appears
in the benchmark artifacts, it refers to
the defined transfer-inclusive processing
sequence rather than to the execution time
of a complete encryption application.

This distinction prevents the isolated kernel
throughput from being interpreted as the
throughput of a complete host--device workflow.

The archived data also preserve selected
host-observed H2D and D2H intervals.

These measurements include synchronization
effects and should not be interpreted as
direct measurements of pure PCIe transmission
time.

Likewise, subtracting an independently
measured resident interval from the pipeline
interval provides only an approximate
description of additional overhead.

It does not independently identify transfer
latency or provide a complete decomposition
of GPU processing time.


\subsection{Timing and Throughput Calculation}
\label{subsec:timing_throughput}

CPU elapsed time is measured using Python's
high-resolution monotonic
\texttt{time.perf\_counter\_ns()} interface.

The recorded values represent elapsed
wall-clock time with nanosecond numerical
representation, which does not imply
nanosecond measurement accuracy.

GPU resident execution is measured using
CUDA event timing and the synchronization
required to obtain completed device-side
execution intervals.

This approach accounts for the asynchronous
nature of CUDA kernel dispatch
\cite{cupyPerformance,nvidiaBestPractices}.

The prepared-buffer pipeline uses a
host-observed wall-clock interval around
the synchronous H2D--kernel--D2H sequence.

Therefore, resident and pipeline times
differ in both the operations included
and the timing mechanism employed.

For a workload of $N$ processed bytes
and elapsed time $T$ in seconds,
throughput is calculated as

\begin{equation}
R = \frac{N}{10^6 T},
\label{eq:throughput}
\end{equation}

where $R$ is expressed in decimal
megabytes per second (MB/s).

Workload sizes are expressed in binary
units, such as KiB and MiB.

For paired CPU--GPU measurements,
the speedup factor is

\begin{equation}
S_{\mathrm{CPU/GPU}} =
\frac{T_{\mathrm{CPU}}}{T_{\mathrm{GPU}}},
\label{eq:cpu_gpu_speedup}
\end{equation}

where the two intervals refer to
matching cryptographic workloads
and explicitly identified measurement
boundaries.

A value above one indicates that the
measured GPU path is faster than the
selected CPU reference.

A value below one indicates that
the selected CPU reference is faster.

All reported GPU speedups distinguish
resident and pipeline execution.

Likewise, comparisons identify whether
the CPU denominator corresponds to
software AES or hardware-assisted AES-NI.

These distinctions are necessary because
a result obtained against software-only
CPU execution may differ substantially
from the result obtained against an
AES-NI reference.

For small messages, absolute latency
is an important complementary metric
because fixed launch and synchronization
costs can dominate the measured interval.


\subsection{Experimental Sessions and Statistical Aggregation}
\label{subsec:statistical_analysis}

The principal study contains five sessions
per platform, with twenty timing repetitions
for each measured configuration.

The session is the primary experimental
replication unit.

Let $T_{s,r}$ denote the elapsed time
recorded in session $s$ and repetition $r$.

The session-level median is

\begin{equation}
\widetilde{T}_{s} =
\operatorname{median}_{r}(T_{s,r}).
\label{eq:session_median}
\end{equation}

The principal study-level elapsed-time
estimate is calculated as the median of
the five session-level medians:

\begin{equation}
\widetilde{T}_{\mathrm{study}} =
\operatorname{median}_{s=1,\ldots,5}
\left(\widetilde{T}_{s}\right).
\label{eq:study_median}
\end{equation}

The throughput estimator is calculated
independently from the recorded throughput
observations.

For a given session,

\begin{equation}
\widetilde{R}_{s} =
\operatorname{median}_{r}(R_{s,r}).
\label{eq:session_throughput}
\end{equation}

The study-level throughput estimate is

\begin{equation}
\widetilde{R}_{\mathrm{study}} =
\operatorname{median}_{s=1,\ldots,5}
\left(\widetilde{R}_{s}\right).
\label{eq:study_throughput}
\end{equation}

For paired CPU--GPU comparisons,
the session-level speedup is

\begin{equation}
S_s =
\frac{
\widetilde{T}_{\mathrm{CPU},s}
}{
\widetilde{T}_{\mathrm{GPU},s}
}.
\label{eq:session_speedup}
\end{equation}

The aggregated paired speedup is

\begin{equation}
\widetilde{S}_{\mathrm{study}} =
\operatorname{median}_{s=1,\ldots,5}(S_s).
\label{eq:study_speedup}
\end{equation}

This estimator is not generally equivalent
to the ratio of independently aggregated
CPU and GPU throughput values.

The nonlinear behavior of the median
means that separate aggregation followed
by division need not reproduce the median
of paired session-level timing ratios.

The selected procedure preserves
the intended CPU--GPU pairing.

Measurements from different platforms
are aggregated independently.

Between-session variability is reported
descriptively using observed ranges,
interquartile ranges, and coefficients
of variation where appropriate.

For session-level estimates $x_s$,
the sample coefficient of variation is

\begin{equation}
\mathrm{CV} =
\frac{
\sqrt{
\frac{1}{n-1}
\sum_{s=1}^{n}
(x_s-\bar{x})^2
}
}{
\bar{x}
},
\qquad n=5.
\label{eq:session_cv}
\end{equation}

Directional consistency is also recorded
as the number of sessions supporting
the corresponding performance advantage.

For example, a GPU speedup exceeding
one in all five sessions is reported
as a $5/5$ directional result.

This is a descriptive observation,
not a significance test or a
guarantee of future behavior.

The twenty within-session repetitions
are not treated as twenty additional
independent sessions.

No measurements are discarded solely
because they appear extreme.

The five-session design provides
evidence of repeatability within the
tested configurations while limiting
formal statistical generalization.

These conventions are consistent
with recommendations for rigorous
computer-system performance evaluation
\cite{kalibera2013rigorous,
hoefler2015scientific,
mytkowicz2009wrong}.


\subsection{Experimental Artifacts and Traceability}
\label{subsec:experimental_artifacts}

The benchmarking framework preserves
multiple categories of experimental
evidence.

The archived artifacts include raw
timing observations, per-session
summaries, cryptographic validation
records, environment descriptions,
resolved benchmark configurations,
source-code snapshots, and
cross-session aggregates.

Raw observations preserve the
individual measured intervals rather
than only the final summary values.

Session summaries record the statistics
associated with each workload
configuration.

Validation records document whether
the relevant cryptographic and backend
checks succeeded.

Environment and configuration records
identify the hardware, software,
random seeds, and benchmark parameters
associated with each execution.

Source snapshots and SHA-256 hashes
support identification of the active
benchmark implementation used by
the three primary studies.

The archived active Python and CUDA
sources match across the selected
platforms.

Nevertheless, source identity does
not imply identical native binaries,
runtime libraries, or GPU execution
behavior.

The complete three-platform study
contains fifteen validated sessions
and 18,000 raw timing observations.

An independent offline analysis
recomputed the saved session-level
and study-level statistical estimators
from the corresponding raw records.

No numerical discrepancies were
detected within the specified
floating-point tolerances.

The analysis also verified the
expected sessions, workloads,
configuration groups, validation
outcomes, source identities, and
required saved artifacts.

These checks establish internal
consistency and permit subsequent
reanalysis.

However, artifact completeness and
matching hashes cannot independently
prove the absence of systematic timing
bias or establish identical behavior
across different computing platforms.


\subsection{Methodological Scope and Limitations}
\label{subsec:methodological_limitations}

The methodology supports performance
comparisons between documented
AES execution paths under the
tested conditions.

It does not establish universal
CPU--GPU rankings or guarantee
application-level acceleration.

First, the three platforms differ
in processor models, GPU models,
memory systems, operating systems,
drivers, runtime libraries, and
cryptographic software versions.

Consequently, the observed differences
cannot be attributed solely to an
operating system, GPU class, or
library revision.

Second, one computing system or
cloud allocation was studied per
platform, with five study sessions
for each configuration.

The resulting sample supports
descriptive assessment of
within-platform repeatability,
but does not establish performance
characteristics of all devices
in the corresponding product classes.

Third, the CPU references
characterize the selected software
and hardware-assisted library
implementations.

The collected execution metadata
support the intended AES-NI
backend selection but do not
constitute a direct processor
instruction trace.

Fourth, the tested CUDA kernels
represent a baseline implementation
and a lightweight optimized-v1
candidate.

They are not claimed to represent
the highest achievable GPU AES
throughput.

Fifth, the resident and
prepared-buffer pipeline paths
measure different operations.

Resident execution excludes
transfers, while pipeline execution
includes the specified synchronous
data movement but excludes buffer
preparation and other application
costs.

The measured pipeline therefore
does not characterize complete
file encryption, network encryption,
or authenticated application
processing.

Sixth, the workloads consist
of five discrete sizes executed
in a fixed order.

Observed local throughput changes,
including those around 16~MiB,
cannot be assigned to a specific
hardware or software mechanism
without additional controlled
instrumentation.

Potential explanations involving
memory behavior, driver scheduling,
clock variation, or thermal effects
remain hypotheses rather than
established conclusions.

Seventh, the principal heterogeneous
study evaluates AES-128 encryption
in ECB and CTR modes.

It does not establish performance
for all key lengths, authenticated
encryption modes, multi-stream
pipelines, or arbitrary application
workloads.

The broader retrospective experiments
concerning DES, TDEA, AES-GCM,
reduced-keyspace demonstrations,
and avalanche behavior are
interpreted separately from the
principal heterogeneous benchmark.

Finally, statistical interpretation
is based primarily on descriptive
session-level estimates.

Observed ranges and directional
consistency counts do not establish
statistical significance or
population-wide reliability.

Within these limits, the study
provides an auditable comparison
of CPU software execution,
CPU AES-NI, device-resident
CUDA computation, and synchronous
transfer-inclusive GPU processing.

Its principal methodological
contribution lies in separating
cryptographic correctness,
measurement scope, statistical
aggregation, and practical
interpretation of heterogeneous
AES acceleration.
