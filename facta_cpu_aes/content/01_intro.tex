\section{Introduction}
\label{sec:intro}
The Advanced Encryption Standard (AES) is a central component of systems that protect stored and transmitted data~\cite{fips197}. Its computational cost matters in applications ranging from bulk storage encryption to services processing short messages. In these settings, encryption shares processor time and memory bandwidth with other application functions. Understanding its performance therefore requires attention both to the cipher implementation and to the software through which an application invokes it.

Modern processors provide dedicated cryptographic instructions, while libraries select among implementations according to processor capabilities and software configuration. However, applications also initialize cipher contexts, allocate output buffers, convert data representations and transfer control between programming languages. A measurement taken within a native encryption routine excludes some of this work. A measurement around a higher-level call includes more of it. Both are useful, but each describes a different part of the computation.

This distinction matters when evaluating native libraries through Python interfaces. Libraries implementing the same AES mode may perform different preparation and data-handling operations. Their measured difference can consequently reflect cipher implementation, interface design and timer placement. These contributions must be distinguished before using a benchmark to select a library or estimate application capacity.

The central research question is: \emph{how much of an optimized AES implementation's throughput advantage survives when the measurement boundary expands from encryption processing to a broader software operation?} We investigate this question through validated measurements from a Windows x86-64 and an Oracle Cloud Arm64 instance. AES-128 in counter (CTR) mode provides the primary workload. Separate Windows experiments with cipher block chaining (CBC) and Galois/Counter Mode (GCM) provide supporting evidence on key length and authenticated message processing~\cite{sp80038a,sp80038d}.

This study contributes an empirical characterization of the persistence of AES implementation advantages across software measurement boundaries. Two complementary findings support this contribution: the Arm64 results quantify sensitivity to library and capability selection, while the Windows results quantify the attenuation of OpenSSL's relative advantage when broader operation costs are included. CBC and GCM observations establish why this interpretation must also account for message size and cryptographic functionality. The contribution is an evidence-based account of the limits of translating cipher-level performance into software-operation performance, rather than a new AES implementation or a measurement of production application performance.

Comparisons are made within each host and workload, with the timing differences stated explicitly. Section~\ref{sec:related} places the study in the context of AES implementation and benchmarking research. Section~\ref{sec:method} describes the experimental setup and estimators. Section~\ref{sec:results} presents the results and their interpretation, followed by broader implications, limitations and future work in Section~\ref{sec:discussion}. Section~\ref{sec:conclusion} concludes the paper.
