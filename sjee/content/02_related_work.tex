\section{Related Work and Research Gap}
\label{sec:related_work}

Early contributions by Manavski~\cite{manavski2007cuda} and Harrison and
Waldron~\cite{harrison2007aes} established the feasibility of AES execution on programmable GPU
architectures. Subsequent work investigated how parallel processing, memory organization, and
architecture-specific optimization affect encryption throughput. The available parallelism
depends partly on the encryption mode: ECB permits independent block transformations, while CTR
generates keystream from distinct counter values~\cite{dworkin2001modes}. Both expose
independent work for GPU threads when buffers are sufficiently large. ECB is unsuitable for
protecting general structured data and serves here only as a controlled performance reference.

Iwai et al.~\cite{iwai2012acceleration} examined thread granularity, memory organization, and
the interaction between computation and data transfers, including overlapping transfers with
computation. Their CUDA implementation achieved approximately 35~Gbit/s for device-side AES
processing and approximately 22.5~Gbit/s for transfer-aware execution. These results demonstrate
that the execution boundary and transfer strategy affect the reported encryption rate. Wang and
Chu~\cite{wang2019gpu} investigated lookup-table-based AES implementations and GPU execution
strategies. Tezcan~\cite{tezcan2021optimization} examined shared-memory optimization and
bank-conflict avoidance, reporting AES-128 encryption throughput of 878.6~Gbit/s on an NVIDIA
RTX~2070~Super.

More recent work has explored bit-sliced cipher representations. A 2024
study~\cite{bitsliced2024gpu} reported high-performance AES-CTR and AES-ECB execution on desktop
and embedded NVIDIA platforms. Together, these studies demonstrate the computational
capabilities of optimized GPU implementations. Their reported rates must nevertheless be
interpreted within their respective measurement boundaries: device-side encryption throughput
does not directly specify the rate at which an application can receive, encrypt, and deliver
data. It also does not establish whether offloading improves performance relative to the host
processor available in a particular system.

That comparison depends on the CPU implementation. Dedicated instructions such as AES-NI reduce
the cost of AES transformations~\cite{intel2012aesni} and provide a hardware-assisted baseline
for evaluating GPU offloading. Lee et al.~\cite{lee2010debunking} demonstrated that conclusions
about heterogeneous acceleration depend strongly on the optimization level of the
implementations being evaluated. Their findings support using an appropriately accelerated CPU
reference when deciding whether GPU offloading offers an additional processing benefit.
Accordingly, comparing GPU encryption with conventional unaccelerated software cannot establish
an advantage over the host's hardware-assisted AES path. The reference must represent the
execution path against which an offloading decision will actually be made, and the comparison
remains specific to the implementations evaluated.

Data location further determines which costs enter that decision. Gregg and
Hazelwood~\cite{gregg2011data} showed that CPU--GPU performance evaluation requires explicit
consideration of data movement. An advantage for device-resident input may shrink when both
input and output cross the host--device boundary. CUDA guidance recommends minimizing
unnecessary transfers, using appropriate synchronization, and considering overlap between
communication and computation~\cite{nvidiaBestPractices,harris2012overlap}. The transfer-aware
AES work of Iwai et al.~\cite{iwai2012acceleration} demonstrates that this concern is already
established in GPU cryptographic processing.

For storage-oriented workloads, the Apache Parquet encryption specification
supports the 	exttt{AES\_GCM\_CTR\_V1} construction, in which encrypted data
pages motivate independently initialized CTR streams~\cite{parquet_encryption_spec}.
Independent pages expose parallel work but require a distinct nonce/counter domain
for each page. Unlike a single contiguous CTR stream, page-aware execution must
map each GPU thread to a page-local counter without counter reuse. GPU-assisted
GCM research~\cite{schonberger2011gpu,lee2025parallelgcm} is related, but
accelerating AES-CTR alone does not provide authentication or a complete file-format implementation.

Assessing whether an observed advantage is repeatable also requires control of experimental
variability. Mytkowicz et al.~\cite{mytkowicz2009wrong} showed that experimental conditions can
introduce systematic bias and alter performance results. Kalibera and
Jones~\cite{kalibera2013rigorous} emphasized the importance of accounting for variability across
multiple levels of experimental replication, while Hoefler and
Belli~\cite{hoefler2015scientific} discussed scientifically defensible performance evaluation of
parallel computing systems. These contributions provide a methodological basis for determining
whether an acceleration is repeatable under the conditions tested. These studies motivate
reporting repeated observations and their execution context rather than relying on the highest
throughput measurement. For cryptographic workloads, functional correctness must additionally be
verified before timings are accepted as evidence of encryption performance.

These studies motivate correctness-gated measurements, session-level variability,
and explicit definitions of what is timed. The unresolved practical question is
whether GPU computation remains attractive against a native hardware-accelerated
CPU when independently encrypted pages and host--device transfers are measured.
We address this with a same-runtime Tesla T4 study, while retaining a compact
historical cross-platform comparison as context rather than treating it as
statistically paired evidence.
