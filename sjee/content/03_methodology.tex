\section{Methodology}
\label{sec:methodology}

The evaluation compares AES-128 encryption using hardware-assisted CPU AES-NI and a validated
CUDA implementation. CTR is the primary workload; ECB provides a controlled reference for
mode-dependent implementation behavior. Both modes process contiguous buffers under the same
validation and measurement protocol. Three complete hardware--software configurations are
evaluated: two Windows systems and a Linux-based cloud allocation.

\subsection{Independent ARM64 CPU Control}
\label{sec:oracle-arm}
An additional CPU-only study was conducted on an Oracle Cloud ARM64
instance with two available vCPUs (Arm Neoverse-N1) and no GPU. It is
reported as an architecture and implementation control, not as a fourth
CPU--GPU pair. Five single-worker sessions measured AES-128-CTR using
PyCryptodome, native OpenSSL 3 EVP with the default CPU capabilities,
and an OpenSSL run with \texttt{OPENSSL\_armcap=0}. A separate
five-session, two-worker experiment recorded aggregate operation-envelope
throughput. All comparisons in this subsection are limited to the Oracle
host and their explicitly named measurement intervals. In particular,
\texttt{OPENSSL\_armcap=0} disables multiple Arm acceleration capabilities,
so its performance difference is not an isolated measurement of a single
AES instruction. Native EVP transform-only timing excludes allocation,
Python interoperation, and output conversion; operation-envelope timing
includes additional host-side costs. The two-worker results are aggregate
throughput, not a twofold reduction in a single request's latency.

The CPU reference uses PyCryptodome with hardware-assisted AES-NI explicitly enabled
\cite{pycryptodome,intel2012aesni}. Native backend initialization was checked for both modes;
executed processor instructions were not traced directly. The GPU path uses the validated
\texttt{cuda\_baseline} kernel through CuPy's custom kernel interface \cite{cupyRawKernel}. Each
CUDA thread processes one 16-byte AES block, with 128 threads per CUDA block. These paths are
selected from a broader campaign that evaluated additional implementations. The analysis retains
their original execution context, including interleaved jobs excluded from the selected results.

Cryptographic validation precedes acceptance of timing measurements. Known-answer tests and
consistency checks against CPU reference operations use the AES specification and mode
definitions \cite{nist2023aes,dworkin2001modes}. The archived records document successful CUDA
execution and agreement with expected outputs. Executions failing the required checks are
excluded from valid performance results. Experimental configuration, measurement-record
completeness, and source-code identity are also verified.

The archived harness validates each measured output against the CPU reference outside the timed
call, in addition to the initial validation gate. An output mismatch stops performance export.
For each size, mode, and repetition, a single synthetic message is replayed across the paired
backends. Plaintext and a 16-byte key are generated from the seeded random generator. The
initial CTR block consists of eight generated bytes followed by eight zero bytes. The CPU CTR
call uses an empty nonce and interprets the full initial counter as a big-endian integer.

Pair identifiers record size, mode, and repetition. A SHA-256 digest of the concatenated key,
counter, and plaintext records the common input material. Raw records also retain the session
identifier, seed, backend, mode, measurement scope, job order, global execution order, and
validation flag. These fields allow the selected CPU and GPU observations to be matched without
pooling observations from different sessions. Previous output buffers are released outside the
next timed call.

The retained dataset is checked against the archived file hashes. For each platform, mode, size,
and repetition, the selected observations contain one CPU transformation, one resident GPU
measurement, and one pipeline measurement with matching input digests. Each configuration group
contains all twenty recorded repetitions. Throughput is independently checked against the
corresponding byte count and recorded time before session-level aggregation. Resident records
specify one kernel iteration, and the GPU records identify pinned host memory. The verification
reconstructs the aggregates from raw records rather than relying solely on the saved summary
tables.

The experiment uses five input sizes:

\begin{equation}
  N \in \{1~\mathrm{KiB},\,16~\mathrm{KiB},\,1~\mathrm{MiB},
  \,16~\mathrm{MiB},\,32~\mathrm{MiB}\}.
\end{equation}

Corresponding CPU and GPU executions use deterministic input generation and matching plaintext,
encryption keys, and mode-specific parameters. Each platform has five study sessions with random
seeds 2003--2007. For each measured configuration, five warm-up executions precede twenty
recorded repetitions; warm-ups are excluded from the timing records. Each session contains
thirty selected configuration groups, comprising two modes, five sizes, and three execution
boundaries. With twenty observations per group, each session contributes 600 observations,
giving

\begin{equation}
  3 \times 5 \times 30 \times 20 = 9\,000
\end{equation}

raw timing observations across the three systems. Workload sizes execute in ascending order,
while mode and backend/\allowbreak measurement-scope jobs are shuffled using the session seed.
Benchmark jobs run sequentially. The selected observations were extracted from the existing
campaign, without rerunning or reordering the benchmark schedule.

Three timing boundaries are retained:

\begin{enumerate}
  \item \textbf{CPU AES-NI transformation.} The interval measures the host encryption call,
    including output allocation performed by that call. Cipher construction and key setup are
    excluded.
  \item \textbf{GPU resident execution.} CUDA events measure a single kernel launch with input
    already in device memory. Host-to-device and device-to-host transfers are excluded.
  \item \textbf{Prepared-buffer GPU pipeline.} The interval measures the synchronous host-driven
    sequence of host-to-device transfer, CUDA kernel execution, device-to-host transfer, and
    synchronization required to complete these operations.
\end{enumerate}

CPU execution and the GPU pipeline are timed with Python's monotonic high-resolution
\texttt{time.perf\_counter\_ns()} interface. Resident execution uses CUDA event timing with the
required synchronization, following CUDA and CuPy measurement guidance
\cite{nvidiaBestPractices,cupyPerformance}. Thus, the CPU and pipeline intervals are measured
from the host, while the resident interval measures device-side execution.

The prepared-buffer pipeline uses pinned host memory and preallocated device buffers, prepared
before the timed interval. Its processing stages are represented as

\begin{equation}
  T_{\mathrm{pipeline}} =
  T_{\mathrm{H2D}} +
  T_{\mathrm{kernel}} +
  T_{\mathrm{D2H}} +
  T_{\mathrm{overhead}},
\end{equation}

where H2D and D2H denote host-to-device and device-to-host transfers, and the final term covers
additional costs within the measured boundary. This expression describes the stages of the
synchronous operation; it is not a decomposition calculated by adding separately aggregated
component measurements. Recorded transfer-component intervals include synchronization effects
and are not isolated measurements of physical PCIe transmission time.

GPU compilation, memory allocation and pinning, initial host-side input staging, key
preparation, and application-level input/output are excluded from the pipeline interval.
Transfers and computation are not overlapped using multiple asynchronous CUDA streams. Resident
execution and prepared-buffer processing are measured separately, with the latter including the
movement needed to process a host-resident buffer and return its output. No network
input/output, packet aggregation, or authenticated-encryption operation is included in these
measurements.

Elapsed processing time, throughput, and host-relative GPU acceleration are summarized at
session level. For an input of $N$ bytes and elapsed time $T_{s,r}$ in seconds at repetition $r$
of session $s$, throughput in decimal MB/s is

\begin{equation}
  R_{s,r} = \frac{N}{10^6 T_{s,r}},
\end{equation}

Input sizes use binary KiB and MiB units. Time and throughput medians are calculated
independently within each session, then aggregated across the five session estimates:

\begin{equation}
  \widetilde{T} =
  \operatorname{median}_{s}
  \left(\operatorname{median}_{r} T_{s,r}\right),
  \qquad
  \widetilde{R} =
  \operatorname{median}_{s}
  \left(\operatorname{median}_{r} R_{s,r}\right).
\end{equation}

Throughput is summarized from the recorded per-repetition throughput values rather than obtained
by inverting the aggregated latency statistic. For the corresponding CPU and GPU executions,
acceleration is calculated from the paired session-level timing medians:

\begin{equation}
  S_s =
  \frac{\widetilde{T}_{\mathrm{AES\mbox{-}NI},s}}
       {\widetilde{T}_{\mathrm{GPU},s}},
  \qquad
  \widetilde{S} =
  \operatorname{median}_{s=1,\ldots,5}(S_s).
\end{equation}

Here, $\widetilde{T}_{\mathrm{AES\mbox{-}NI},s}$ and $\widetilde{T}_{\mathrm{GPU},s}$ denote
within-session median times for the same platform, mode, and input size. GPU resident and
pipeline speedups are calculated separately against the corresponding AES-NI time. Values of
$S_s>1$ indicate a faster GPU path, while values below one indicate a faster CPU reference. The
reported $\widetilde{S}$ is the median of five paired ratios, not a ratio of independently
aggregated CPU and GPU throughput values.

The analysis reports session ranges, interquartile ranges, sample coefficients of variation, and
counts of sessions with $S_s>1$. For five ordered session estimates, the interquartile range is
the fourth minus the second value; the sample coefficient of variation is the sample standard
deviation divided by the mean. An advantage in every session is recorded as $5/5$ directional
consistency. These are descriptive statistics, not confidence intervals or formal significance
tests. The twenty repetitions within a session are not treated as independent sessions, and
measurements are not removed merely because they appear extreme.

The use of repeated sessions, paired workloads, and documented execution conditions follows
recommendations on experimental bias and hierarchical variability in performance measurement
\cite{mytkowicz2009wrong,kalibera2013rigorous,hoefler2015scientific}. Raw observations and their
provenance are retained for verification of the session estimates and acceleration calculations.


\subsection{Native CPU Baseline and Same-Runtime T4 Validation}
\label{sec:evp-method}
The historical three-platform study used a hardware-assisted PyCryptodome host
path. A later, independent T4 study compared that path, a native OpenSSL 3 EVP
AES-128 implementation, and the original validated CUDA baseline on the same
runtime allocation. The five sessions used seeds 2003--2007, five warm-ups and
20 measurements per size and mode; buffers ranged from 1~KiB to 32~MiB.
Results from this newer study are paired only within its own sessions.

Native \emph{CPU transform time} was measured inside C around encryption with
prepared contexts/output; it excludes the Python-to-C call, allocation and
cipher setup. GPU \emph{resident time} is a CUDA-event compute interval with
prepared device buffers. GPU \emph{prepared pipeline time} includes payload
host-to-device transfer, kernel execution, device-to-host transfer and
synchronization, but excludes GPU allocation, staging, key expansion and output
conversion. These boundaries are useful for determining whether prepared GPU
processing repays transfer cost, but they do not provide identical wrapper
costs or full application latency. CPU operation-envelope measurements include
additional setup/allocation/copying and are retained only as asymmetric
diagnostics.

\subsection{Independent-Page CTR Batch Experiment}
\label{sec:page-method}
A separate T4 campaign encrypted $N\in\{1,4,16,32\}$ independently managed
1~MiB pages, for total sizes of 1, 4, 16 and 32~MiB. Each page used a separate
96-bit synthetic test nonce concatenated with a 32-bit big-endian initial
counter of one. The counter is advanced \emph{within} each page and never
carried into another page's nonce. The page-aware CUDA kernel assigns blocks
to their corresponding page and encrypts all pages in one launch using the
unchanged historical AES round implementation. A native OpenSSL EVP path
processes the page contexts sequentially on one calling CPU thread.

An equal-size continuous CTR stream forms the control. For each size and
repetition the page and continuous controls share plaintext and key but use
distinct nonce domains. The experiment validates ciphertext independently
against a CPU reference, including published vectors, page boundaries, counter
carry and overflow guards. Five T4 sessions (seeds 2003--2007) each include
five warm-ups and 20 measurements for all four batch sizes, both layouts and
three scheduled measurement paths. This yields 2,400 measured observations
plus 600 warm-ups. Actual execution order, input digests, source hashes,
software versions and session identity are retained. All reported speedups
use the CPU duration divided by GPU duration: values greater than one favor
the GPU. Five session medians, not pooled individual repetitions, form the
primary descriptive replication units. The study is synthetic and measures
batch completion rather than application request latency.
