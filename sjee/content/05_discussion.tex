\section{Discussion}
\label{sec:discussion}

\subsection{Practical Meaning of Offloading}

The results answer the offloading question conditionally. T600 and T4 demonstrate that a
prepared-buffer GPU pipeline can outperform AES-NI for a measured CTR workload. GTX and T4 ECB
show why neither GPU availability nor high resident throughput is sufficient to justify that
choice. For data already on the device, resident execution is relevant; for host-resident input
and output, the pipeline comparison is more informative. Neither substitutes for measuring the
application's complete processing path.

The T4 mode contrast also shows why CPU-relative speedup and absolute GPU throughput must be
reported separately. Similar GPU rates can produce very different speedups when host CPU modes
behave differently. The observations do not identify a particular library version, CPU feature
or cloud mechanism as the cause. A controlled same-host investigation would be needed to
separate these possibilities.

For telecommunications, the positive large-buffer results motivate evaluation of bulk or
batched processing, not a claim that individual packets are encrypted faster on a GPU. Packet
assembly, queueing, state management, authentication and output delivery can change the
trade-off. AES-NI remains a relevant reference for latency-sensitive workloads; a system should
select an execution path using its actual data location and processing requirements.

\subsection{Limitations and Future Work}

The study evaluates one host or cloud allocation per configuration and five sessions per host.
It describes repeatability within these runs, not population-wide reliability or statistical
significance. Hardware, operating systems, drivers and libraries differ simultaneously, so the
comparison cannot isolate an operating-system or GPU-class effect. Matching archived source
bytes do not establish identical compiled code or execution conditions.

The CPU reference is a selected library path, not the fastest possible multithreaded AES
service, and the CUDA implementation is not a GPU performance limit. The reported subset was
selected from a broader interleaved campaign; removing other paths from the article does not
remove their possible effects on the original execution state. Source provenance and integrity
checks support auditability but cannot eliminate timing bias or environmental interference.

The fixed ascending size order confounds size with elapsed execution time. The 16~MiB feature
cannot be attributed to cache, driver, clock or thermal behavior from the available evidence.
Randomized, more densely sampled sizes with synchronized instrumentation would help distinguish
these hypotheses. Additional hosts and repeated cloud allocations would improve external
validity, while controlled CPU-mode measurements would clarify the T4 disparity.

Finally, ECB and CTR are not authenticated encryption. AES-GCM adds GHASH and associated
security processing~\cite{dworkin2007gcm}; its performance and that of complete network
protocols do not follow from these results. Application evaluations must include authentication,
preparation and delivery costs.
