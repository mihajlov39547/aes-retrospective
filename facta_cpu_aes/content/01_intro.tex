\section{Introduction}
The Advanced Encryption Standard (AES) is used across data storage, software services, embedded devices and communication systems. Its standardized round operations are independent of processor choice, but its measured execution time is not. Modern CPUs may use dedicated cryptographic instructions; software libraries dispatch to different implementations; application frameworks may allocate output storage, initialize contexts and marshal data at different points. A quoted throughput figure can therefore reflect a cryptographic primitive, an application wrapper, or a combination of both.

This ambiguity becomes particularly pronounced when implementations cross a foreign-function boundary. A native library can process an already allocated buffer with a preinitialized context, whereas a Python-facing API can include argument handling and allocation. Comparing the resulting durations without stating their scopes risks turning a claim about a specific API into an unsupported claim about an algorithm or processor. Conversely, measuring only the native transform underestimates the elapsed time of a caller that must assemble a complete encryption operation.

The present work investigates a narrower question than heterogeneous GPU acceleration: \emph{how strongly do AES implementation paths and timing boundaries shape CPU encryption measurements on two instruction-capable architectures?} We use already completed experimental campaigns: AES-128 ECB/CTR measurements from Windows x86-64 and Oracle Cloud Arm64, historical AES-CBC experiments covering 128-, 192- and 256-bit keys, and independently validated AES-GCM measurements on Windows. No new experiments were performed for this manuscript. In particular, results from different modes or hosts are not combined into a unified speedup estimate.

The paper has three contributions. First, it documents the magnitude of implementation-path sensitivity on Arm64, including a constrained OpenSSL capability-mask control rather than an unqualified assertion about the AES instruction alone. Second, it distinguishes the native transform from a broader operation envelope on the Windows CPU, using measurements from the same software environment. Third, it analyzes existing AES-CBC and AES-GCM evidence to demonstrate how key length and authentication change throughput within their own explicitly specified workloads. These results motivate a reporting framework in which the cipher mode, implementation, scope, and replication unit accompany each reported performance figure.

This is a retrospective analysis of available datasets, not an attempt to introduce a new cipher or claim a universal processor ranking. All numerical claims are tied to existing experiment outputs; where datasets are not identically instrumented, the limitation is stated explicitly.
