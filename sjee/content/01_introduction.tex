\section{Introduction}

Telecommunications infrastructure must protect increasing volumes of data while maintaining
throughput and acceptable processing latency. Communication gateways, network services, and
distributed processing systems therefore require efficient cryptographic operations. The
Advanced Encryption Standard (AES), specified in NIST FIPS~197 \cite{nist2023aes}, is a
fundamental building block of symmetric encryption. Its practical performance depends on
hardware acceleration, execution strategy, and data movement between processing resources, as
well as the cryptographic algorithm.

Hardware-assisted CPU encryption provides the reference against which an alternative processing
path must be evaluated. Graphics processing units (GPUs) offer parallel execution that can
benefit workloads containing many independent AES operations. Counter (CTR) mode permits
independent counter blocks to be encrypted in parallel to generate keystream
\cite{dworkin2001modes}, making it suitable for investigating GPU-assisted bulk encryption.
Large buffers and collections of independent data units are potential workloads for
telecommunications-oriented systems that already contain general-purpose GPUs. Such systems
could use existing heterogeneous computing resources for bulk encryption without requiring a
dedicated cryptographic accelerator. Whether this is beneficial depends on the costs of moving
the workload through the GPU as well as the throughput of the encryption operation itself.

Using these resources for encryption introduces host-to-device transfers, kernel execution,
synchronization, and transfers back to host memory. These costs can reduce or eliminate the
computational advantage of parallel execution. The relevant question is therefore whether
GPU-assisted AES processing provides a reproducible bulk-throughput improvement over
hardware-accelerated CPU execution, and which workload, platform, and data-movement conditions
determine that improvement. The study distinguishes performance with data already resident in
GPU memory from performance that includes synchronous host--device transfers and
synchronization.

This distinction also affects the interpretation of potential processing strategies. Encrypting
a contiguous buffer, aggregating independent requests, and operating on device-resident data
involve different data-placement and execution costs. Batching may provide more parallel work
per invocation, but its usefulness depends on workload size and application latency
requirements. A favorable result for one execution boundary does not establish an advantage for
the others; each must be assessed against the available host implementation.

The study evaluates validated AES-128 implementations in Electronic Codebook (ECB) and CTR modes
across three heterogeneous computing configurations. CTR is the primary workload of interest,
while ECB provides a controlled reference for independent block processing. Hardware-assisted
CPU AES-NI serves as the baseline. Cryptographic correctness verification, controlled inputs,
paired execution conditions, repeated measurement sessions, and explicit timing boundaries
support the comparison. Section~\ref{sec:methodology} specifies the implementations, workload
sizes, and session-level analysis.

The contribution is experimental evidence identifying conditions under which GPU-assisted bulk
AES processing improves throughput, including cases where an advantage remains after synchronous
data movement. The measurements also identify configurations in which transfer costs or host
implementation characteristics prevent consistent improvement. The common validation and
measurement protocol provides a reproducible basis for assessing these outcomes across the
tested systems. The study evaluates existing encryption approaches rather than introducing a new
AES algorithm. Both favorable and unfavorable acceleration outcomes are used to delimit the
operating conditions supported by the measurements. The results characterize the evaluated CPU
and GPU paths; they do not establish a universal hardware advantage or the maximum throughput
attainable by either architecture.

For telecommunications, bulk data protection, workload aggregation, and device-resident
processing are potential applications of these findings. Their application-level effectiveness
remains untested. In particular, improved AES-CTR buffer processing does not demonstrate
acceleration of complete network security protocols. Authenticated encryption additionally
requires authentication processing, while practical protocols introduce packet handling,
cryptographic state management, and data-delivery costs. These operations, along with batching
and queueing latency, require separate evaluation before the measured bulk-processing
improvements can be extended to telecommunications applications.

Section~\ref{sec:related_work} reviews GPU AES implementations, CPU--GPU comparison methods, and
the evidence needed to assess offloading. Section~\ref{sec:methodology} describes the
experimental design, validation, timing boundaries, and statistical analysis.
Section~\ref{sec:results} presents the measured acceleration outcomes, and
Section~\ref{sec:discussion} examines their practical constraints and potential
telecommunications applications. Section~\ref{sec:conclusion} summarizes the findings.
