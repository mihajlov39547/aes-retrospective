\section{Discussion}
\label{sec:discussion}

\subsection{The Specific Favorable Case: Data Already on the GPU}
The positive result is precise: for 32 independently encrypted 1~MiB pages,
one CUDA resident AES-128-CTR launch takes approximately 3.714~ms, whereas
native OpenSSL EVP requires approximately 8.362~ms for the prepared sequential
CPU transformation. The measured $2.251\times$ ratio makes GPU execution a
credible compute-stage candidate when plaintext is already GPU-resident and
the encrypted result is needed on the device for another processing stage.
This is not a claim that an ordinary host-memory encryption service becomes
$2.251\times$ faster: the resident interval excludes data placement, GPU
allocation and preparation, and a complete multi-stage application has not
been benchmarked.

Potential workload classes include GPU-native analytics pipelines, pipelines
that prepare columnar buffers on the GPU before encryption, and device-side
processing that passes the resulting ciphertext to a later GPU operation.
The common factor is \emph{avoided payload round trips}, not the mere presence
of a GPU. Such placement can be attractive only if input data originate on the
device or would need to move to it for other work anyway, and if the required
output does not have to return immediately to the CPU. Where plaintext starts
in host RAM and ciphertext is consumed by a host process, the tested prepared
pipeline takes approximately 9.153~ms versus 8.362~ms for CPU transformation:
the CPU is faster at these declared boundaries.

\subsection{A Measured Data-Movement Budget, Not an Application Speedup}
The 32~MiB prepared GPU pipeline is approximately 0.791~ms slower than the
prepared CPU transformation, based on the displayed session-level median
durations. This difference describes the margin to parity for the measured
configuration, not an empirically achieved optimization. The approximately
5.418~ms transfer component demonstrates that data movement is large relative
to AES kernel execution; its separately reported median is not directly
substitutable into a single-iteration latency equation. Avoiding transfers
could make GPU-resident processing competitive, but the exact crossover
requires a new workload-level experiment including data preparation, input
residency, output placement, any subsequent consumer, and buffer lifetime.

The ratio of CPU operation-envelope to GPU prepared-pipeline time is not a
symmetrical end-to-end comparison: CPU allocation and setup are included,
whereas GPU allocation, key upload, pinned-memory staging and final conversion
are excluded. It must not be used to claim an application-level speedup.
A second caution is that native OpenSSL EVP timings exclude the Python
wrapper, unlike parts of the GPU path. The present study therefore provides
a well-defined prepared-workload comparison rather than a common application
API benchmark.

\subsection{Independent Pages and Practical Storage Workloads}
Correct independent CTR processing is more than slicing a continuous stream:
each logical page needs its own nonce/counter domain, and the counter must not
cross the domain boundary. The page-aware CUDA implementation verifies these
conditions and processes a batch in one launch. At 32~MiB, the measured GPU
pipeline throughput differs by less than 1\% from the continuous control;
hence handling page boundaries does not impose a large penalty in this
specific kernel. The observation does not imply that page batching is faster
than separately launching the pages: no separate-per-page launch baseline was
included, and the CPU processes the pages sequentially.

The Parquet \texttt{AES\_GCM\_CTR\_V1} design~\cite{parquet_encryption_spec} motivates the page geometry, but
the experiment is not a Parquet writer, reader or encryptor. Format metadata,
AAD, authentication, key management, compression and nonce-generation rules
remain absent. Raw CTR encryption is malleable and provides no integrity
protection. Practical storage deployment therefore requires a complete
format-compliant and authenticated workflow; AES-CTR throughput alone cannot
support security or end-to-end speedup claims about such a system.

\subsection{Why the CPU Baseline Matters}
The historical $4.761\times$ T4 result used a PyCryptodome-based host interval.
The fresh T4 campaign measured $5.586\times$ against PyCryptodome but only
$0.942\times$ against native OpenSSL at the prepared GPU boundary. The native
implementation makes the CPU substantially more competitive. Because library
versions, API overhead and timing boundaries differ, this is evidence of
baseline sensitivity rather than a proof that the old measurement was invalid.
Historical GTX 1650 Ti and T600 findings remain useful for showing diversity
across complete configurations but cannot substitute for a same-runtime
OpenSSL-controlled study on those machines.


\subsection{Cross-Architecture Evidence from Oracle ARM64}
The Oracle CPU-only control strengthens the baseline-sensitivity argument:
on the same ARM64 machine, native OpenSSL-default AES-128-CTR and the
recorded PyCryptodome or capability-masked paths differ markedly.
This does not show that ARM is intrinsically faster than x86, nor that
all of the observed gap is due to AES instructions: implementations,
Python interfaces, capability masking, and measurement scopes also
matter. The two-worker envelope result additionally illustrates that
aggregate throughput and single-request latency answer different
questions. Thus, the portable finding is a methodological and
architectural constraint: report an optimized, capability-aware host
reference and the actual operation boundary before attributing an
advantage to accelerator hardware. A future controlled ARM study should
trace executed cryptographic instructions, harmonize native call
boundaries, and examine additional core counts and AES-256.

\subsection{Generalizability, Constraints and Future Work}
The relevant engineering decision is whether a specific pipeline can retain
plaintext and ciphertext on the GPU while maintaining its functional and
security requirements. The following hypotheses are actionable but untested:
(1) a GPU-first columnar transformation followed by resident encryption could
avoid round-trip payload transfers; (2) encryption before another GPU-resident
consumer could make cipher output placement beneficial; and (3) pipelined
transfers or batch reuse might reduce the effective movement cost for
host-resident data. None is demonstrated by the present one-launch benchmarks.

The next experiment should implement an actual producer--encrypt--consumer
CUDA pipeline, with device-resident buffers, an explicit encrypted-output
consumer, correctness validation, and a CPU counterpart completing the same
functional work. It should account for input acquisition, context/key and
nonce-table setup, GPU allocation, transfers actually needed, synchronization
and output disposition. A separate one-page-at-a-time GPU launch baseline
would isolate the genuine \emph{batching} effect from the present continuous
CTR control. Format-level work would integrate Parquet's full encryption
rules, authenticated metadata, and key management, then report file or query
throughput and latency. AES-GCM, AES-256, overlapping streams and multiple
simultaneous requests are further experiments, not consequences of AES-128-CTR
results.

The present measurements use one CUDA implementation and a single-threaded
native CPU comparator, five sessions, synthetic data and a shared cloud
platform. Kernel-level and transfer timings use different instrumentation;
GPU scheduling, memory placement, host contention and CPU dispatch affect
results. No instruction-level trace was captured. The work neither ranks all
available CPUs/GPUs nor estimates a universal cross-platform crossover.
