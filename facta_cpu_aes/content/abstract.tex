AES throughput depends on implementation paths and on which software costs a benchmark includes. This paper quantifies how much of an optimized implementation's advantage persists when timing expands from encryption processing to a broader operation. We analyze validated CPU measurements from Windows x86-64 and Oracle Cloud Arm64, supported by separate AES-CBC and AES-GCM campaigns. At 32 MiB, default OpenSSL AES-CTR on Arm64 achieved approximately nineteen times the throughput of the evaluated alternative paths. On Windows, the OpenSSL-to-PyCryptodome throughput ratio decreased from approximately 1.93 at the transform boundary to 1.23 for the instrumented operation. The latter retained 26.7\% of OpenSSL's transform throughput and 41.8\% of PyCryptodome's. These findings show that cipher-level advantages need not transfer proportionally to surrounding software operations, motivating workload-specific library evaluation with explicit timing boundaries.
