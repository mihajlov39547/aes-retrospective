\section{Methodology}
\label{sec:methodology}

The central study measures AES-128-CTR encryption of host-resident
continuous buffers and groups of independently encrypted 1~MiB pages on a
Linux x86-64 Google Colab instance with an NVIDIA Tesla T4 (compute
capability 7.5). The CPU comparator is native OpenSSL 3 EVP with AES-NI
capability enabled; PyCryptodome serves as an implementation sensitivity
control. The CUDA implementation retains the original AES rounds and
executes 128 threads per block. All comparisons in the main study use the
same live runtime, deterministic input material, and ciphertext validation.

Earlier benchmarking covered a GeForce GTX 1650 Ti/i5-10300H on Windows,
an NVIDIA T600/i7-11850H on Windows, and a Tesla T4/Xeon under Linux.
These records remain historical context only: they used PyCryptodome host
intervals that are not equivalent to the new native OpenSSL boundary and
cannot be paired with the later campaigns. An independent Oracle Cloud
Neoverse-N1 ARM64 CPU-only control was also collected; it informs the
interpretation of library/capability sensitivity but contributes no GPU
speedup ratios. Platform and library versions and source hashes are
recorded with the released experiment artifacts.

\subsection{Native CPU Baseline and Same-Runtime T4 Validation}
\label{sec:evp-method}
The historical three-platform study used a hardware-assisted PyCryptodome host
path. A later, independent T4 study compared that path, a native OpenSSL 3 EVP
AES-128 implementation, and the original validated CUDA baseline on the same
runtime allocation. The five sessions used seeds 2003--2007, five warm-ups and
20 measurements per size and mode; buffers ranged from 1~KiB to 32~MiB.
Results from this newer study are paired only within its own sessions.

Native \emph{CPU transform time} was measured inside C around encryption with
prepared contexts/output; it excludes the Python-to-C call, allocation and
cipher setup. GPU \emph{resident time} is a CUDA-event compute interval with
prepared device buffers. GPU \emph{prepared pipeline time} includes payload
host-to-device transfer, kernel execution, device-to-host transfer and
synchronization, but excludes GPU allocation, staging, key expansion and output
conversion. These boundaries are useful for determining whether prepared GPU
processing repays transfer cost, but they do not provide identical wrapper
costs or full application latency. CPU operation-envelope measurements include
additional setup/allocation/copying and are retained only as asymmetric
diagnostics.

\subsection{Validation, Timing, and Statistical Treatment}
\label{sec:measurement-policy}
The experiments distinguish three operational questions. First, a
resident-kernel interval tests the encryption computation achievable
when the payload has already been placed in device memory. Second, a
prepared-pipeline interval tests encryption when the plaintext begins
in host memory and the encrypted payload must return to the host;
this interval includes synchronous host--device transfers and GPU
completion. Third, a native OpenSSL transform interval supplies an
optimized, hardware-assisted host reference without including buffer
allocation or high-level language binding costs. We deliberately avoid
labelling this collection as a symmetric application-level benchmark.
The independent-page test does not include a GPU implementation of
page-level metadata protection, authentication, or a Parquet writer.

Every configuration uses deterministic, matched inputs and a correctness
gate before recorded timing. Timed ciphertext is also checked against
an independently computed reference outside the measurement window.
An invalid counter range, repeated nonce within a logical batch, or
output mismatch invalidates the observation. GPU launches operate on
preallocated buffers; the prepared pipeline includes both payload
transfer directions, but does not include the prior creation of pinned
buffers or encryption-key expansion. Consequently, a difference
between pipeline and resident sample medians is not interpreted as a
pure PCIe transmission measurement.

For a buffer of $B$ bytes and duration $t$ seconds, throughput is
$B/(10^6t)$ in decimal MB/s. Within a session, the primary speedup
estimator is the ratio of median CPU and GPU durations for the same
configuration; five such session estimates are summarized by their
median and range. Matched per-repetition ratios are retained as a
separate estimator rather than silently mixed with ratios of medians.
No warm-up durations enter the summary, and no adverse observations
or outliers are deleted. Since five sessions are repeated executions
on one cloud allocation rather than independent hardware samples,
these statistics describe consistency on the tested system and do not
support population-level confidence claims.

\subsection{Independent-Page CTR Batch Experiment}
\label{sec:page-method}
A separate T4 campaign encrypted $N\in\{1,4,16,32\}$ independently managed
1~MiB pages, for total sizes of 1, 4, 16 and 32~MiB. Each page used a separate
96-bit synthetic test nonce concatenated with a 32-bit big-endian initial
counter of one. The counter is advanced \emph{within} each page and never
carried into another page's nonce. The page-aware CUDA kernel assigns blocks
to their corresponding page and encrypts all pages in one launch using the
unchanged historical AES round implementation. A native OpenSSL EVP path
processes the page contexts sequentially on one calling CPU thread.

An equal-size continuous CTR stream forms the control. For each size and
repetition the page and continuous controls share plaintext and key but use
distinct nonce domains. The experiment validates ciphertext independently
against a CPU reference, including published vectors, page boundaries, counter
carry and overflow guards. Five T4 sessions (seeds 2003--2007) each include
five warm-ups and 20 measurements for all four batch sizes, both layouts and
three scheduled measurement paths. This yields 2,400 measured observations
plus 600 warm-ups. Actual execution order, input digests, source hashes,
software versions and session identity are retained. All reported speedups
use the CPU duration divided by GPU duration: values greater than one favor
the GPU. Five session medians, not pooled individual repetitions, form the
primary descriptive replication units. The study is synthetic and measures
batch completion rather than application request latency.
