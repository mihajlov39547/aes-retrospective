
\section{Methodology}
\label{sec:methodology}

The experimental methodology is designed to determine under which operating conditions
GPU-assisted AES processing can improve bulk encryption throughput while accounting for
the overhead associated with accelerator execution. The evaluation focuses on AES-128
encryption, using hardware-assisted CPU AES-NI as the reference and a validated CUDA
implementation as the alternative processing path.

The methodology follows a validation-first approach that combines cryptographic
correctness checks, controlled input workloads, explicitly defined timing boundaries,
repeated measurements, and independent verification of the resulting data. Its purpose
is to identify reproducible acceleration conditions rather than to establish the
maximum theoretical throughput of either processor architecture.

The experimental workloads represent contiguous encryption buffers of different sizes.
They are intended to characterize the computational behavior relevant to bulk data
processing, not to reproduce a complete telecommunications protocol or network
packet-processing pipeline.

The two laptop configurations represent accessible GPU-equipped computing systems,
while the T4 provides a datacenter-oriented environment. The exact model of the
cloud host CPU was not available in the archived environment records. Each
configuration is treated as a complete hardware--software system. Differences
in observed performance cannot be attributed solely to the GPU, operating system,
processor generation, driver, or cryptographic library because these characteristics
were not independently controlled.

The CPU reference uses PyCryptodome with hardware-assisted AES-NI explicitly enabled
\cite{pycryptodome,intel2012aesni}. Native backend initialization was checked for
both evaluated encryption modes. This supports the intended use of AES-NI, although
it does not constitute a direct trace of executed processor instructions. The
GPU implementation is the validated CUDA kernel archived as
\texttt{cuda\_baseline}, executed through CuPy's custom kernel interface
\cite{cupyRawKernel}. The kernel assigns one 16-byte AES block to each CUDA
thread, with 128 threads per CUDA block.

This organization allows independent AES blocks to be distributed across GPU
execution threads. It provides a controlled implementation for evaluating bulk
encryption, but is not claimed to represent the highest attainable CUDA AES
throughput. The selected CPU AES-NI and CUDA execution paths originate from a broader
experimental campaign that also evaluated additional implementations. The
present analysis retains only the paths relevant to the stated research objective.


\subsection{Cryptographic Validation and Workload Design}
\label{subsec:experimental_design}

Functional correctness is established before performance measurements are
accepted for analysis. This requirement ensures that observed throughput
corresponds to a valid implementation of the intended AES transformation.

Validation includes known-answer tests and consistency checks against CPU
reference operations, using the AES specification and the definitions of
the evaluated encryption modes \cite{nist2023aes,dworkin2001modes}. The
archived validation records document successful CUDA execution and
agreement with the expected cryptographic outputs. A failure of the required
checks prevents the corresponding execution from being accepted as a valid
performance result.

Correctness validation is complemented by verification of experimental
configuration, completeness of measurement records, and source-code identity.
Passing cryptographic test vectors does not independently establish that
a timing method is free from measurement bias.The experiment evaluates
AES-128 encryption in Electronic Codebook (ECB) and Counter (CTR) modes.

CTR is the principal mode of interest because independent counter blocks
can be encrypted in parallel, providing a computational structure suitable
for GPU-assisted bulk processing \cite{dworkin2001modes}. ECB
is retained as a controlled reference for independent AES block
transformations. Its inclusion supports analysis of mode-dependent
implementation behavior and must not be interpreted as a recommendation
to use ECB for general application data.

Five input sizes were evaluated:

\begin{equation}
  N \in \{1~\mathrm{KiB},\,16~\mathrm{KiB},\,1~\mathrm{MiB},
  \,16~\mathrm{MiB},\,32~\mathrm{MiB}\}.
  \label{eq:workload_sizes}
\end{equation}

The selected sizes span small encryption requests and larger contiguous
buffers suitable for examining bulk-processing throughput.

These workloads are not equivalent to individual telecommunications
packets. In particular, processing a 32~MiB buffer does not demonstrate
that independently received network packets can be grouped and encrypted
with the same throughput or latency. Corresponding CPU and GPU executions
use deterministic input generation
and matching cryptographic parameters, including plaintext, encryption
key, and mode-specific values.

The experiments use five study sessions per platform with random seeds
2003--2007. Each measured configuration includes five warm-up executions
followed by twenty recorded timing repetitions. Warm-up operations are
excluded from the reported timing records.

The selected analysis contains thirty measured configuration groups per
session, with twenty observations per group. Consequently, each session
contributes 600 observations, giving

\begin{equation}
  3 \times 5 \times 30 \times 20 = 9\,000
  \label{eq:observation_count}
\end{equation}

raw timing observations across the three systems.

Workload sizes are executed in ascending order, while mode and
backend/measurement-scope jobs are shuffled according to the session
seed. Benchmark jobs execute sequentially rather than concurrently.

The retained observations preserve their original execution context,
including interleaved jobs excluded from the present analysis. This
distinction is important because the selected subset was extracted
from an existing experimental campaign rather than generated through
a newly executed benchmark schedule.


\subsection{GPU Processing Paths and Measurement Boundaries}
\label{subsec:measurement_boundaries}

To determine whether GPU acceleration provides a practical processing
benefit, the methodology distinguishes computational execution from
the additional work required to move data through the accelerator.

Three timing boundaries are evaluated.

\begin{enumerate}

  \item \textbf{CPU AES-NI transformation.}
  Measures the host encryption call using the hardware-accelerated
  CPU library path. The interval includes output allocation performed
  by the encryption call but excludes cipher construction and key setup.

  \item \textbf{GPU resident execution.}
  Measures a single CUDA kernel launch operating on data already present
  in device memory. The interval is measured using CUDA events and
  excludes host-to-device and device-to-host transfers.

  \item \textbf{Prepared-buffer GPU pipeline.}
  Measures the synchronous host-driven processing sequence consisting
  of host-to-device transfer, CUDA kernel execution, device-to-host
  transfer, and the synchronization required to complete these operations.

\end{enumerate}

CPU execution and the GPU pipeline are timed using Python's monotonic
high-resolution \texttt{time.perf\_counter\_ns()} interface. GPU resident
execution uses CUDA event timing with the required synchronization,
following CUDA and CuPy measurement guidance
\cite{nvidiaBestPractices,cupyPerformance}.

The prepared-buffer pipeline uses pinned host memory and preallocated
device buffers. These resources are prepared before the timed interval. The
measured GPU processing sequence can be represented conceptually as

\begin{equation}
  T_{\mathrm{pipeline}} =
  T_{\mathrm{H2D}} +
  T_{\mathrm{kernel}} +
  T_{\mathrm{D2H}} +
  T_{\mathrm{overhead}},
  \label{eq:gpu_pipeline_components}
\end{equation}

where H2D and D2H denote the host-to-device and device-to-host stages,
respectively, and the final term represents additional costs within
the measured execution boundary. This expression illustrates the relevant processing stages rather
than a decomposition calculated from separately aggregated measurements.

The pipeline excludes GPU compilation, memory allocation and pinning,
initial host-side input staging, key preparation, and application-level
input/output. It does not implement overlapping transfers and computation
through multiple asynchronous CUDA streams. Consequently, its timing is
broader than device-resident kernel timing,
but it does not represent the complete execution of a telecommunications
application.

The distinction is particularly important for assessing potential
acceleration. A GPU kernel may achieve higher computational throughput
while the additional transfer and synchronization costs reduce or
eliminate the advantage when a complete buffer must move between
host and device. Conversely, applications in which input data are already available
in device memory may have different processing costs. The study
measures these execution scenarios separately rather
than treating kernel throughput as a substitute for broader
processing performance. Recorded transfer-component intervals include synchronization effects.
They therefore cannot be interpreted as isolated measurements of
physical PCIe transmission time.


\subsection{Performance Metrics and Statistical Analysis}
\label{subsec:statistical_analysis}

The principal performance metrics are elapsed processing time,
throughput, and the relative acceleration achieved by the selected
GPU execution path.

For an input of $N$ bytes and elapsed time $T_{s,r}$ measured in
seconds during repetition $r$ of session $s$, throughput is

\begin{equation}
  R_{s,r} = \frac{N}{10^6 T_{s,r}},
  \label{eq:throughput}
\end{equation}

where throughput is expressed in decimal megabytes per second
(MB/s). Input sizes are reported using binary KiB and MiB units.

To account for repeated observations and session-level variation,
the analysis uses hierarchical aggregation.

First, the median elapsed time and throughput are calculated
independently within each session. The principal aggregate
statistics are then calculated across the five session estimates:

\begin{equation}
  \widetilde{T} =
  \operatorname{median}_{s}
  \left(\operatorname{median}_{r} T_{s,r}\right),
  \qquad
  \widetilde{R} =
  \operatorname{median}_{s}
  \left(\operatorname{median}_{r} R_{s,r}\right).
  \label{eq:study_estimates}
\end{equation}

Throughput is summarized directly from the recorded throughput
observations rather than calculated by inverting the aggregated
latency statistic. The acceleration factor is based on the ratio of corresponding
session-level timing medians:

\begin{equation}
  S_s =
  \frac{\widetilde{T}_{\mathrm{AES\mbox{-}NI},s}}
       {\widetilde{T}_{\mathrm{GPU},s}},
  \qquad
  \widetilde{S} =
  \operatorname{median}_{s=1,\ldots,5}(S_s).
  \label{eq:study_speedup}
\end{equation}

A value greater than one indicates that the measured GPU path
completes the corresponding operation faster than the host
AES-NI reference. A value below one indicates that the CPU reference is faster.

The reported acceleration factor is the median of paired
session-level timing ratios, not the ratio of independently
aggregated CPU and GPU throughput values. The study additionally reports session ranges, interquartile
ranges, coefficients of variation, and the number of sessions
supporting a particular performance advantage.

An observed advantage in all five sessions is reported as
$5/5$ directional consistency. This indicates repeatability
within the recorded sessions but does not constitute a formal
statistical significance test. The twenty repetitions within each session are not treated
as twenty independent experimental sessions. Measurements
are not excluded merely because they appear extreme.

This approach follows established recommendations concerning
the influence of experimental conditions and hierarchical
variability on computer-system performance measurements
\cite{mytkowicz2009wrong,kalibera2013rigorous,hoefler2015scientific}.
