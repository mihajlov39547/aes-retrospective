\section{Discussion}
\label{sec:discussion}

The findings of this study extend beyond a comparison of encryption throughput. They provide
empirical evidence that the benefit of GPU-based AES execution depends on the host processor,
cipher mode, workload size, data location, and the operations included within the measurement
boundary. These factors are particularly relevant when cryptographic acceleration is considered
for accessible computing systems, communication infrastructure, and heterogeneous
data-processing platforms.

The principal result is twofold. First, even relatively accessible 4~GB NVIDIA laptop GPUs can
deliver substantial AES-128 acceleration under selected conditions. Second, higher
device-resident throughput does not guarantee that transferring data to and from the GPU will
remain advantageous over a CPU already equipped with AES-NI instructions.

The three-platform evaluation therefore supports neither a universal preference for CPU
execution nor a general recommendation to offload AES to the GPU. Instead, it identifies
measured conditions under which acceleration is beneficial and provides a reproducible procedure
for assessing whether those conditions apply to a particular processing system.

This distinction is important for both technical specialists and system architects. The relevant
deployment question is not simply which processor encrypts data faster, but which execution path
completes the required cryptographic operation at an acceptable cost in throughput, latency,
resource usage, and data movement.

\subsection{When Can GPU Encryption Outperform AES-NI?}
\label{subsec:discussion_scope}

The experimental results provide direct evidence that GPU execution can outperform the selected
hardware-accelerated CPU AES-NI path, including when host--device transfers are incorporated
into the measured processing sequence.

The clearest example among the two tested 4~GB laptop GPUs is the NVIDIA T600 Laptop GPU.

For AES-128 CTR encryption of a 32~MiB buffer, the baseline CUDA prepared-buffer pipeline
achieves a median paired speedup of $1.354\times$ relative to the corresponding CPU AES-NI
transformation on the Intel Core i7-11850H host.

The observed speedup ranges from $1.129\times$ to $1.391\times$ across five study sessions, with
the GPU advantage present in all five.

This represents approximately 26\% lower paired processing latency for the defined benchmark
operation, based on the reported median speedup ratio.

The result demonstrates that GPU offloading can remain advantageous even when the measured
workload includes synchronous host-to-device transfer, CUDA execution, device-to-host transfer,
and synchronization.

However, the result does not establish that the T600 would outperform every optimized CPU
implementation or that the same advantage would persist in a complete telecommunications
application.

The consumer GeForce GTX~1650~Ti presents an equally important counterexample.

At 32~MiB in CTR mode, its baseline CUDA pipeline achieves a $4.566\times$ median speedup over
the selected software CPU AES implementation, but only $0.935\times$ relative to its host's
AES-NI implementation.

The GPU therefore provides substantial acceleration compared with software-only AES without
demonstrating a consistent advantage over the stronger hardware-assisted CPU reference.

The NVIDIA Tesla T4 provides a further contrast.

For the 32~MiB CTR workload, its baseline CUDA pipeline achieves approximately $4.761\times$
speedup relative to the paired host AES-NI implementation, with an advantage observed in all
five sessions.

For ECB mode under otherwise matching conditions, however, the T4 pipeline achieves only
$0.893\times$ the host AES-NI reference.

This large difference in relative speedup does not correspond to an equally large difference in
GPU encryption throughput. At 32~MiB, T4 baseline pipeline throughput is approximately 3.71~GB/s
for both ECB and CTR.

Instead, the host AES-NI execution paths exhibit markedly different mode-dependent throughput.
The measured ECB-to-CTR AES-NI throughput ratio on the T4 host is approximately 5.38, compared
with approximately 1.26 on the two Windows hosts.

The underlying cause of the T4 CPU disparity was not isolated. Therefore, it would be
inappropriate to attribute the observed CTR advantage exclusively to GPU hardware, CUDA
execution efficiency, or a particular software-library version.

Taken together, the results establish a qualified but practically meaningful conclusion: GPU AES
execution can outperform a hardware-accelerated CPU reference, including in a transfer-inclusive
pipeline, but only under specific combinations of hardware, workload, mode, and implementation.

The distinction between absolute throughput and host-relative speedup is essential when
selecting computing resources.

\subsection{Why Parallel Execution and Data Location Matter}
\label{subsec:discussion_aesni}

AES-128 CTR is well suited to parallel execution because the input blocks used to generate the
keystream can be processed independently, provided the counter values are assigned correctly and
are not reused with the same key.

A CUDA implementation can distribute these independent block computations across many GPU
threads.

This execution structure offers an architectural reason why GPUs may provide substantial
throughput for large collections of independent blocks. Earlier research has also investigated
AES acceleration on CUDA devices \cite{iwai2012acceleration}.

However, the experiments do not isolate GPU parallelism as the sole cause of the observed
speedup. The measured result reflects the interaction between the CUDA implementation, host CPU,
memory behavior, runtime environment, and timing boundary.

Modern CPUs provide an alternative form of acceleration through dedicated cryptographic
instructions.

AES-NI reduces the cost of selected AES operations by executing cryptographic transformations
through processor-supported instructions. Consequently, a software-only AES implementation is
not an adequate standalone baseline for deployment decisions on AES-NI-capable processors.

This principle is consistent with earlier work showing how comparisons between optimized CPU and
GPU implementations depend on the selected implementations and their execution conditions
\cite{lee2010debunking}.

The present study demonstrates this effect directly. A GPU advantage measured against software
AES can become substantially smaller or disappear when the CPU reference uses AES-NI.

Data location introduces another important distinction.

For the 32~MiB workloads, the GPU resident paths outperform the paired AES-NI CPU transformation
on all three systems, for both CUDA implementations and both evaluated AES modes, in all five
sessions.

Nevertheless, the corresponding prepared-buffer pipeline measurements are less favorable.

On the GTX~1650~Ti, the pipeline retains approximately one quarter of resident throughput at
32~MiB. The corresponding proportions are approximately 46--48\% on the T600 and about 40\% on
the T4.

These values do not measure pure PCIe transfer efficiency. They express the reduction in
observed throughput between different timing boundaries, including the additional host-driven
operations represented by the synchronous pipeline.

This interpretation is consistent with the findings of Gregg and Hazelwood~\cite{gregg2011data},
who emphasized that the location of application data and the cost of movement are essential to
meaningful CPU--GPU comparisons.

In practical terms, a system whose data are already resident on the GPU may avoid some transfers
that are necessary in a host-memory-based workflow.

Conversely, a system that receives every input buffer in CPU memory and requires every encrypted
output to return immediately to the CPU may obtain less benefit from the accelerator.

The results therefore support data placement as a central architectural consideration, although
the potential benefits of persistent GPU residency in complete applications remain to be
measured.

\subsection{Implications for Telecommunications Systems}
\label{subsec:discussion_implications}

The present measurements do not establish a consistent GPU pipeline advantage for the smallest
workloads. Thus, they do not justify routing every small network packet through a discrete GPU.

The measured 32~MiB results demonstrate that substantial processing volumes can favor the GPU
under particular configurations. The T600 result shows that this advantage is not restricted to
datacenter-class GPUs.

Nevertheless, a single contiguous 32~MiB benchmark buffer is not equivalent to a collection of
independently authenticated network packets.

Batch preparation, packet metadata, cryptographic state, nonce assignment, authentication,
output delivery, and queueing delays must be accounted for before extrapolating to a real
communication system.

The 32~MiB results should therefore be interpreted as evidence that large aggregate processing
workloads warrant GPU evaluation, not as proof that individual telecommunication packets will be
encrypted faster on the GPU.

\subsection{Authenticated Encryption and Practical Security}
\label{subsec:discussion_gcm}

The heterogeneous performance study focuses on AES-128 ECB and CTR because these modes permit
controlled evaluation of independent block-level computation.

This scope is useful for benchmarking, but it does not encompass all requirements of secure
communication.

In particular, ECB does not provide appropriate confidentiality for general structured
application data.

CTR provides confidentiality when correctly configured and used, but does not by itself provide
message authentication or integrity protection.

Practical network protocols generally require additional cryptographic properties, frequently
provided by authenticated-encryption constructions.

AES-GCM combines counter-mode AES processing with authentication based on
GHASH~\cite{dworkin2007gcm}.

The study does not include a validated GPU AES-GCM pipeline.

Therefore, measured GPU ECB and CTR throughput cannot be treated as AES-GCM throughput, and the
T600 or T4 CTR speedups cannot be transferred directly to TLS or IPsec deployments.

A complete AES-GCM GPU implementation would require evaluation of AES counter processing, GHASH,
authentication-tag generation and verification, nonce management, and the relevant transfer and
application-processing costs.

\subsection{Future Research Directions}
\label{subsec:discussion_future}

The findings identify several directions for subsequent research, without requiring those
extensions to establish the principal contribution of the present study.

A first direction is application-level evaluation of cryptographic offloading in communication
systems.

Such research could measure AES-GCM within representative network-processing workloads,
including packet batching, authentication, queueing latency, and delivery of processed data.

This would determine whether the advantages observed for large AES-CTR buffers persist when
complete security and communication operations are included.

A second direction is adaptive CPU--GPU execution selection.

The observed differences between small inputs, larger workloads, resident computation, and
transfer-inclusive processing suggest that heterogeneous schedulers could benefit from
workload-aware decisions.

A practical investigation would evaluate throughput and latency together, rather than assuming
that the fastest bulk encryption path also minimizes response time for individual packets.

A third direction concerns data-movement-aware system design.

Asynchronous execution, overlapping transfers and computation, device-resident processing, and
supported direct-I/O technologies could alter the cost of accelerator offloading.

The present measurements provide a synchronous reference against which such implementations
could be assessed, but do not predict their attainable speedup.

A fourth direction is broader validation across independent hardware and software systems.

Additional CPU libraries, multithreaded AES-NI implementations, newer GPUs, and dedicated
network cryptographic accelerators would help determine which observations remain stable across
architectures.

More densely sampled and randomized workload sizes, combined with synchronized instrumentation,
could also help investigate the observed non-monotonic throughput behavior and improve
performance prediction.
