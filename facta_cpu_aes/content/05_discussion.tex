\section{General Discussion}
\label{sec:discussion}
\subsection{Implications for encryption performance}
The results identify three aspects of AES performance that should be considered together: the selected implementation, the work included in the timer and the cryptographic service being provided. The Arm64 measurements show a large difference between library configurations. The Windows measurements show that the relative advantage narrows at a broader software interface. The CBC and GCM experiments show that key length, authentication and message size further shape the processing cost. A useful performance statement must therefore specify these conditions rather than attach a single rate to AES or to a processor architecture.

This interpretation also clarifies the optimization question. When cipher processing dominates, a more efficient native implementation can offer substantial benefits. When other work occupies a larger part of the operation, optimizing that work becomes more important. The present data demonstrate the difference between measurement scopes, but do not determine the optimal balance for a particular application. That balance depends on its message distribution, buffer ownership, context lifetime and required security functionality.

\subsection{Limitations and scope of generalization}
The study contains repeated observations from one Windows laptop and one Arm64 cloud instance. Differences in processor configuration, operating system, OpenSSL version, scheduling and virtualization prevent a controlled architectural comparison. Processor affinity, dynamic frequency scaling and cloud contention were not fully controlled. Repeated use of prepared buffers also differs from a cold-cache or continuous streaming workload. Five sessions describe repeatability under these conditions, not variability across a population of machines.

The measurement interfaces impose additional limits. PyCryptodome and OpenSSL transform timers include different language-interface costs, while the broader operation contains benchmark diagnostics. Capability inspection does not establish which instructions executed, and the Arm64 mask changes several capabilities simultaneously. The earlier CBC and GCM campaigns use their own timing conventions. These constraints permit comparisons within the stated scopes, but limit causal attribution and prevent combining all results into one acceleration factor.

Functional validation establishes agreement with expected outputs and, for GCM, rejection of the tested modifications. It does not establish resistance to timing leakage or other implementation attacks. Similarly, the study does not evaluate key management, nonce generation in a deployed service, energy consumption or latency under concurrent client load. Performance conclusions apply to the measured operations and should be considered alongside those separate requirements.

The transferable finding is methodological: a comparison should preserve the workload and identify the timed interval relevant to its intended use. Numerical rankings remain specific to the tested configurations, even when the same evaluation method is applied elsewhere.

\subsection{Applications and analogies in other domains}
The findings are relevant to CPU-based storage encryption, secure messaging and data-processing services. A service handling large buffers can evaluate whether native processing and reusable output storage reduce its total cost. A service handling short authenticated messages should assess setup and verification together with payload processing. These are hypotheses for application evaluation; the experiments do not demonstrate a speedup in a complete storage system or communication protocol.

A similar distinction arises in compression, numerical computing and machine-learning inference. A fast compression routine may be surrounded by buffer allocation and data copying; an optimized numerical kernel may require data conversion; an inference engine may spend substantial time on preprocessing and request handling. These examples illustrate the same question of measurement scope. They are conceptual analogies rather than additional empirical findings of this study.

A reproducible benchmark should report the mode, key size, payload distribution, nonce and AAD policy, library configuration, buffer policy and timer placement. Session-level variation should accompany aggregate rates. These details allow readers to assess whether a result represents the operation their application needs.

\subsection{Future research}
A first priority is a matched native benchmark on both architectures, with identical entry points and explicit alternatives for context and output-buffer reuse. Instruction tracing and independently controlled capability settings would then help separate AES processing from vector and authentication-related optimizations. Such experiments would provide stronger explanations for the observed library differences.

A second priority is authenticated encryption on Arm64 under the same nonce, AAD and verification policy used on Windows. Measuring object construction, payload processing and complete request latency separately would connect the present GCM observations to application behavior. Finally, evaluation within a storage or messaging service should include realistic message distributions, concurrency and input/output costs. This would test whether the implementation advantages observed here remain useful when encryption is one stage of a larger workflow.
