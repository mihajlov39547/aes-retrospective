
\section{Introduction}
\label{sec:introduction}

The increasing volume of data processed by modern telecommunications infrastructure creates
a continuing demand for efficient cryptographic operations. Communication gateways, network
services, distributed processing systems, and data-intensive applications must protect
information while maintaining adequate throughput and acceptable processing latency.
The Advanced Encryption Standard (AES) remains a fundamental building block of symmetric
encryption, with its algorithmic specification defined by NIST FIPS~197
\cite{nist2023aes}. However, the performance of AES in practical systems depends not only
on the cryptographic algorithm but also on the available hardware acceleration, execution
strategy, and movement of data between processing resources.

Modern processors provide dedicated AES instructions, commonly known as AES-NI, which
substantially accelerate the execution of AES transformations \cite{intel2012aesni}.
Graphics processing units (GPUs), on the other hand, offer a highly parallel execution
environment capable of processing large numbers of independent computational tasks.
This capability is particularly relevant to the Counter (CTR) mode of AES, where
independent counter blocks can be encrypted in parallel to generate the required
keystream \cite{dworkin2001modes}. For telecommunications-oriented workloads involving
large data buffers or collections of independent data units, GPU acceleration may
therefore provide an additional processing option.

The potential benefit is especially interesting for systems that already contain
general-purpose GPUs but rely primarily on the host CPU for cryptographic operations.
Such systems could potentially employ existing heterogeneous computing resources to
increase bulk encryption throughput without requiring a dedicated cryptographic
accelerator. However, transferring an encryption workload to a GPU introduces costs
associated with host-to-device data movement, kernel execution, synchronization, and
returning the processed data to host memory. These operations can reduce or eliminate
the computational advantage of parallel execution. Consequently, high device-level
AES throughput does not necessarily imply improved performance for the complete
processing path \cite{gregg2011data,nvidiaBestPractices}.

Previous research has established the feasibility of GPU-accelerated AES and
demonstrated substantial improvements through parallel processing, memory
organization, and architecture-specific optimization
\cite{manavski2007cuda,harrison2007aes,iwai2012acceleration,
wang2019gpu,tezcan2021optimization}. Earlier studies have also investigated
the overlapping of host--device transfers with computation, demonstrating
that communication overhead is an established concern in GPU cryptographic
processing \cite{iwai2012acceleration}. Nevertheless, the throughput achieved
by highly optimized kernels does not, by itself, determine whether GPU
offloading is beneficial for a particular system, especially when the
host processor already provides hardware-assisted AES execution.

For telecommunications infrastructure, the relevant problem is therefore
not simply how fast AES can execute on a GPU, but under which operating
conditions GPU-assisted processing can improve the throughput of a
cryptographic workload while accounting for the costs of transferring
data through the accelerator. This distinction becomes important when
considering different processing strategies, such as encrypting data
directly on the CPU, processing large buffers on a GPU, or organizing
independent workloads into batches suitable for parallel execution.
Although batching and device-resident processing offer potential
architectural benefits, their effectiveness depends on workload size,
data placement, execution overhead, and application-level latency
requirements.

The central research question addressed in this study is whether
GPU-assisted AES processing can provide a reproducible improvement
in bulk encryption performance over hardware-accelerated CPU execution,
and which workload, platform, and data-movement conditions determine
the applicability of that improvement. Particular attention is given
to distinguishing improvements obtained from isolated GPU computation
from those that remain measurable when the processing path includes
synchronous host--device transfers and synchronization.

To investigate this question, the study evaluates validated AES-128
implementations in Electronic Codebook (ECB) and Counter (CTR) modes
across three heterogeneous computing configurations. ECB is included
as a controlled reference for independent block processing, while
CTR represents the primary parallelizable encryption workload of
interest. The experimental protocol combines cryptographic correctness
verification, controlled inputs, paired execution conditions, repeated
measurement sessions, and explicitly defined timing boundaries.
Hardware-assisted CPU AES-NI serves as the reference for determining
whether GPU execution provides an additional performance benefit.

The study contributes experimentally verified evidence about the
conditions under which GPU-assisted bulk AES processing can be
advantageous, together with a reproducible methodology for identifying
the limits of that advantage. Rather than proposing a new AES algorithm
or claiming a universally superior implementation, the contribution
lies in establishing measurable operating conditions under which
existing GPU resources can improve encryption throughput despite
the additional costs of data movement. Equally important, the study
identifies configurations in which these costs or host implementation
characteristics prevent a consistent improvement.

The significance of these findings extends to the design of
heterogeneous telecommunications processing architectures.
Large-volume encryption, suitable workload aggregation, and
data-resident processing represent potential areas in which
GPU resources could complement CPU cryptographic instructions.
However, improved AES-CTR buffer processing must not be interpreted
as demonstrated acceleration of complete network security protocols.
For example, AES-GCM incorporates authentication processing in
addition to counter-mode encryption \cite{dworkin2007gcm}, and
practical protocol implementations introduce further costs
associated with packet handling, cryptographic state, and
data delivery. These requirements must be evaluated separately
before extending the findings to complete telecommunications
applications.

The remainder of the paper develops this argument systematically.
Section~\ref{sec:related_work} examines existing GPU AES acceleration
techniques and the methodological limitations of reported performance
results. Section~\ref{sec:methodology} describes the experimental
design, validation procedures, execution boundaries, and statistical
analysis. Section~\ref{sec:results} presents the measured operating
conditions and observed acceleration outcomes.
Section~\ref{sec:discussion} considers their implications for
telecommunications-oriented processing, practical constraints,
and future applications. Finally, Section~\ref{sec:conclusion}
summarizes the principal findings and their significance for
GPU-assisted AES acceleration.
