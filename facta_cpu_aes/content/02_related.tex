\section{Background and Related Work}
\subsection{AES implementation paths and instruction support}
AES is specified by FIPS 197 and is instantiated with 128-, 192- or 256-bit keys, requiring 10, 12 or 14 encryption rounds, respectively~\cite{fips197}. Modes of operation govern how successive blocks and counters are processed, not merely which key length is used. CBC encryption has inter-block dependencies, whereas CTR encrypts successive counter blocks and combines the resulting stream with the plaintext~\cite{sp80038a}. ECB is useful here only as an implementation-path diagnostic, not as a recommendation for sensitive data.

Intel's AES-NI instructions provide an acceleration path for AES rounds~\cite{intelaesni}. Armv8 implementations can expose hardware AES features through the instruction-set architecture, but availability and actual library dispatch must be established on the measured system. OpenSSL's EVP interface offers a relatively stable cipher abstraction whose internal implementation may differ with providers, CPU features and OpenSSL version~\cite{openssl}. The PyCryptodome package similarly exposes AES operations through a Python API and native code, with behavior that cannot be assumed identical to EVP~\cite{pycryptodome}. Thus an observed difference is initially an \emph{implementation-path difference}, not proof that a particular instruction is solely responsible.

\subsection{Measurement scope and authenticated encryption}
Meaningful comparisons require matched payloads, validated ciphertexts and explicit placement of timestamps. A transform-only duration can exclude cipher setup and allocation, while an operation-envelope duration includes a more complete software call. Both may be useful, but they answer different questions and should not be placed into a single speedup column without qualification. Native measurements may also exclude Python entry overhead that another backend includes.

Authenticated encryption introduces a separate distinction. Galois/Counter Mode combines CTR-style encryption with an authentication computation and can verify a tag during decryption~\cite{sp80038d}. A GCM processing rate therefore measures more functionality than unauthenticated CBC or CTR. The authentication tag, associated data, and encryption context may be outside the byte-count numerator even when their processing is within the timer. Treating these rates as interchangeable AES-throughput figures would be misleading.

The gap addressed here is primarily \emph{reporting and interpretation}: the same CPU, algorithm family and message size can yield dramatically different advertised throughput because of implementation and instrumentation decisions. Rather than proposing a new accelerated implementation, this article organizes existing validated observations around the exact execution boundaries that produced them.
