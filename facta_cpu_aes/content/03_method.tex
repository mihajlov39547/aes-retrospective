\section{Methodology and Experimental Setup}
\label{sec:method}
\subsection{Platforms, datasets and correctness checks}
The Windows system used an Intel Core i5-10300H (four cores, eight logical processors), Python 3.12.10, PyCryptodome 3.23.0 and verified 64-bit OpenSSL 3.6.5 libraries. The Oracle Cloud instance used a Neoverse-N1-class Arm64 processor with two available virtual CPUs, Python 3.12.3, PyCryptodome 3.23.0 and OpenSSL 3.0.13. Platform metadata, capability settings and source hashes are preserved in the experimental records.

The primary campaigns evaluated AES-128 at 1 KiB, 16 KiB, 1 MiB, 16 MiB and 32 MiB. CTR provides the main workload; archived ECB measurements served as implementation diagnostics. Each configuration used five sessions with seeds 2003--2007, five warm-up repetitions and 20 measured repetitions per session. Known-answer and differential checks established ciphertext correctness before samples were accepted.

Separate earlier Windows campaigns evaluated CBC with 128-, 192- and 256-bit keys and GCM with 128- and 256-bit keys. Both used five seeded sessions, three warm-up repetitions and 20 measured repetitions. We retain the CBC results at 10 MiB and GCM results at 1 KiB, 16 KiB, 1 MiB, 16 MiB and 100 MiB. GCM used 96-bit nonces, 128-bit tags and 16 bytes of AAD, without nonce reuse for distinct messages under one key within a session. Validation included known-answer checks and rejection of modified ciphertext, tags and AAD.

\subsection{Implementation paths and timing scopes}
Both CTR transform measurements use prepared output buffers. OpenSSL timestamps inside a compiled wrapper delimit EVP Update/Final processing; PyCryptodome's transform interval includes Python dispatch and its internal foreign-function interface. The resulting rates describe different interfaces, rather than isolated AES instruction costs.

The \emph{instrumented operation}, named \texttt{operation\_envelope} in the records, measures the Python call to the benchmark routine and assignment of its result. It includes input checks, allocation, bindings, setup, transformation, cleanup, output conversion and applicable diagnostics and bookkeeping. The subsequent ciphertext comparison is outside the timer. This boundary is broader than transformation, but is not an uninstrumented application request. Windows provides both intervals for each library.

On Arm64, \texttt{OPENSSL\_armcap=0} disables multiple optimized capability paths. Default and masked OpenSSL are compared at their common native transform boundary, while the PyCryptodome interval includes additional interface costs. No instruction trace was collected.

CBC retains its original common timing convention for software and AES-NI paths. GCM includes AAD processing, payload processing, output allocation and tag generation or verification, but excludes construction of a fresh cipher object. Its throughput numerator counts payload bytes only. The three campaigns therefore retain distinct operational definitions.

\subsection{Aggregation and interpretation}
For a payload of $B$ bytes processed in $t$ nanoseconds, decimal throughput is
\begin{equation}
 P=\frac{10^3 B}{t}\quad [\mathrm{MB/s}].\label{eq:rate}
\end{equation}
KiB and MiB denote binary payload sizes; MB/s and GB/s denote decimal rates. Each primary result is the median of five session-level rates, calculated as payload bytes divided by the median elapsed time in that session. Session ranges, where reported, describe the smallest and largest of those five medians rather than confidence intervals.

For a reference implementation $A$ and a candidate $B$ measured under a common timing convention, the speedup of $B$ relative to $A$ is
\begin{equation}
 S_{B/A}^{(j)}=\frac{\widetilde t_A^{(j)}}{\widetilde t_B^{(j)}},\qquad
 S_{B/A}=\operatorname{median}_{j=1}^{5}S_{B/A}^{(j)}.\label{eq:ratio}
\end{equation}
Here, $\widetilde t$ denotes the median elapsed time in session $j$; a value above one indicates faster execution by $B$. The CBC acceleration factors use this estimator. Approximate CTR throughput ratios discussed below are ratios of the reported aggregate rates, and are distinguished from session-based speedups. Rounding and the order of aggregation can make these estimators differ.

To characterize attenuation, we calculate the OpenSSL/PyCryptodome throughput ratio separately at each boundary. We also calculate, for each library, its instrumented-operation throughput divided by its transform throughput. These retention ratios use unrounded campaign aggregates and describe changes across timing scopes. They are not estimates of the fractions of time spent on allocation, setup or conversion; causal decomposition would require additional component-level measurements.

Sessions, rather than individual repetitions, are the units of replication. Observations are retained regardless of performance direction. Comparisons across hosts, modes and the separate Oracle worker campaigns are descriptive, not statistically paired.

\subsection{Archive verification and reproducibility}
Reanalysis reads archived data without executing benchmark code. It verifies the selected campaign, five distinct seeds, sample counts, validation status and source hashes. Duplicate single-worker sessions inside the Oracle multicore archive are excluded. Windows contrasts are calculated from unrounded session-summary aggregates.

For Oracle, raw timestamps reconstruct the instrumented-operation boundary in both campaigns. Each worker processes 32 MiB with AES-128-CTR and default OpenSSL. Per repetition, duration is the latest completion minus the earliest start; the numerator is 32 MiB for one worker and 64 MiB for two. Each session rate is this byte count divided by its median duration, followed by the median of five session rates. Native transform rates are neither summed nor compared with these operation rates.

The accompanying \texttt{analyze\_evidence.py} records archive/member hashes, session identifiers, durations and derived ratios in a machine-readable audit. The \texttt{plot\_windows\_boundaries.py} script checks the Windows input hash and regenerates Fig.~\ref{fig:windows}. These scripts reproduce the numerical contrasts from the preserved records without new measurements.
